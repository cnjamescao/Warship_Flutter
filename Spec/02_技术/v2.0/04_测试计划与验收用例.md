# 04｜测试计划与验收用例

## 1. 测试策略与门禁

| 层级 | 工具/方式 | 目标 | 合入门禁 |
| --- | --- | --- | --- |
| Unit | `flutter_test` 纯 Dart | Domain、配置校验、随机、数值 | 必须 |
| Integration | Flame/Flutter harness | 状态、输入、事件、资源生命周期 | 必须 |
| Widget | Flutter widget test | HUD、草案、风险门、结算、低动效的语义、布局和状态 | CI 必须 |
| Golden | Flutter golden | 发布候选的像素级人工复核 | **不进 CI；发布前必须人工复核** |
| Web E2E | 真实浏览器自动化或人工矩阵 | 输入、失焦、音频手势、离线 | 每个发布候选 |
| Performance | profile/release build | 帧时间、对象数、内存、降级 | 每个发布候选 |
| Exploratory | QA 人工 | 可读性、手感、素材、异常恢复 | 每个里程碑 |

所有自动化测试使用显式 `TestContentCatalog`、`FakeClock`、`SeededRandomSource`、`FakeAudioPort`、`InMemoryProgressStore`；不得依赖真实时间、网络、随机顺序或真实音频设备。

## 4. 性能与长稳测试

### 4.1 逻辑性能基线的输入/输出分离（F-42）

`test/fixtures/performance/*.json` 是**只读版本基线**，普通测试与 CI 不得向该目录写入任何测量结果。每次采样报告必须写入 `build/` 或系统临时目录，供诊断查看但不提交。只有显式 `UPDATE_PERF_BASELINE=1` 的专用维护流程可重建 fixture，并须在提交说明中记录运行环境、原因与前后差异。

逻辑耗时会受机器影响，p50/p95/p99 历史数值不是跨机器阻断阈值。普通自动化必须断言：fixture 的 schema/seed/场景完整且未被改写、本次报告完整可读、对象上限/降级/规则正确性守卫通过；另设回归用例，在正常测试前后比较 fixture SHA-256，任何变化即失败。**F-43 已完成**：信息性比较输出基线值、本次值及差值/比例，并先校验基线的 schema、seed、contentVersion、场景时长与对象预算；不能只打印历史值或“见报告”。真实帧时间、内存和发布性能仍按本节第 1–4 条在真机 Release 环境采样，归属 AC-07。

1. 使用内容表中最密集的 130–150 秒段、三层导弹/无人机配置和 Boss P3，连续运行 10 分钟模拟；采集 p50/p95/p99 帧时间、GC、对象数量、音频并发。
2. 强制填满每类对象预算，验证拒绝低优先级特效后预警、HUD、碰撞仍正常。
3. Web profile/release build 在每个目标浏览器测一次；中端移动设备至少一台真机测一次。结果需附设备、浏览器/OS、构建号、seed、采样时长。
4. 30 分钟重复开始/结束/暂停混沌测试后，内存不应持续线性增长；若平台无法精确测内存，至少验证活跃实体、监听和音频句柄归零。

### 5.1 AC-06 固定回放基准

`AC-06` 的长期验收不得用人工目测判定，但**基准首次录制必须来自一次真实人工操作**。指定的研发或 QA 基准操作员在无 debug cheat、无数值修改、无手工编辑 replay 的 release 构建中，用键鼠/触摸完成一次通关；录制全量输入并保留录屏证据。WP-06 完成时，研发必须提交 `test/fixtures/replays/baseline_clear_v1.json`，固定为 `seed=0x4E454F4E0001`、`contentVersion=2.0.6-material-repair` 和正式 `素材/manifest.json` 的 SHA-256，并记录每个逻辑帧的 `InputFrame`、选卡 ID、风险门选项和期望的 `RunEnded` 摘要。成功条件为 180 秒前胜利且全程 `hpDamage=0`（护盾承伤允许）。该文件由技术负责人审核后冻结并纳入版本控制；以后每次构建连续回放 3 次，要求均胜利、HP 从未受伤、事件摘要 hash 一致。发布验收记录必须附基准操作员角色、设备/OS、构建 revision、manifest SHA-256 与录屏路径。不得用脚本搜索、手工篡改 JSON 或假回放替代；若 10 次合规实操均无法获得基准，登记为数值/可通关性缺陷。素材或内容版本变更时，回放必须显式更新版本、manifest hash 和对应变更说明；版本或 hash 不匹配时不得执行旧回放并不得将其结果计为通过。

### 5.2 Golden 人工发布复核

CI 必须以 `--exclude-tags golden` 执行自动化门禁；不得在 CI runner 创建或覆盖基线。每个发布候选由 QA 在固定参考 macOS（记录 macOS、Flutter、显示倍率、分辨率）运行当前 **14 个 Golden**，用同一版本基线进行人工逐张比对；其中必须包含 `boss_fan`、`boss_charge`、`boss_ring`、`boss_laser` 四条。每条 Golden 均须证明真实素材已预载且实际绘制，不接受空缓存回退图。验收记录必须附构建号、执行人、日期、截图或差异图以及每张 Pass/Fail；任何未经产品书面接受的差异均阻断发布。Golden 仍可在研发本机回归，但其二进制结果不得成为跨机器 CI 失败依据。

| CR-03 | 注释 | 公共接口与复杂/高风险逻辑解释原因、约束、边界和取消/失败路径；无逐行复述、过期注释或无说明 TODO | 审查结论与抽样文件清单 |
| CR-04 | 测试质量 | 用例验证真实输入/输出和失败边界；fixture 不自写自读；Golden 使用真实素材；测试不污染工作区 | 测试命令、结果、`git status` |
| CR-05 | 变更可追溯 | 产品/技术/素材/测试变更可相互追溯，提交无无关文件 | PR/提交记录与文档链接 |

CR-01～CR-05 任一 P0/P1 问题未关闭，项目负责人不得签署该功能或版本的技术验收。

## 7. 最终验收规则

P0 任何一项失败即阻断开发里程碑；P1 失败可只在技术负责人记录风险、制定修复版本后进入内部测试，不能标记正式发布。所有 `AC-01` 至 `AC-09`、CR-01 至 CR-05、正式素材许可、Web 回归和性能目标通过后，v2.0 才可验收完成。
