# 04｜测试计划与验收用例

## 1. 测试策略与门禁

| 层级 | 工具/方式 | 目标 | 合入门禁 |
| --- | --- | --- | --- |
| Unit | `flutter_test` 纯 Dart | Domain、配置校验、随机、数值 | 必须 |
| Integration | Flame/Flutter harness | 状态、输入、事件、资源生命周期 | 必须 |
| Widget/Golden | Flutter golden | HUD、草案、风险门、结算、低动效 | 必须（稳定平台） |
| Web E2E | 真实浏览器自动化或人工矩阵 | 输入、失焦、音频手势、离线 | 每个发布候选 |
| Performance | profile/release build | 帧时间、对象数、内存、降级 | 每个发布候选 |
| Exploratory | QA 人工 | 可读性、手感、素材、异常恢复 | 每个里程碑 |

所有自动化测试使用显式 `TestContentCatalog`、`FakeClock`、`SeededRandomSource`、`FakeAudioPort`、`InMemoryProgressStore`；不得依赖真实时间、网络、随机顺序或真实音频设备。

## 4. 性能与长稳测试

1. 使用内容表中最密集的 130–150 秒段、三层导弹/无人机配置和 Boss P3，连续运行 10 分钟模拟；采集 p50/p95/p99 帧时间、GC、对象数量、音频并发。
2. 强制填满每类对象预算，验证拒绝低优先级特效后预警、HUD、碰撞仍正常。
3. Web profile/release build 在每个目标浏览器测一次；中端移动设备至少一台真机测一次。结果需附设备、浏览器/OS、构建号、seed、采样时长。
4. 30 分钟重复开始/结束/暂停混沌测试后，内存不应持续线性增长；若平台无法精确测内存，至少验证活跃实体、监听和音频句柄归零。

## 5. 发布验收记录模板

| 字段 | 必填内容 |
| --- | --- |
| 构建 | git revision、Flutter/Flame 版本、contentVersion、资源 manifest hash |
| 测试环境 | 设备、OS、浏览器、分辨率、网络状态 |
| 自动化 | Unit/Integration/Widget/Golden/Web 的通过数与失败数 |
| 性能 | 场景 seed、对象峰值、p50/p95/p99 帧时间、降级是否发生 |
| 产品验收 | AC-01 至 AC-09 每项 Pass/Fail、证据链接 |
| 素材 | 资产清单版本、许可证检查结果、缺失/占位资源数 |
| 结论 | QA 负责人、技术负责人、日期；任何 Fail 均不得标记发布通过 |

### 5.1 AC-06 固定回放基准

`AC-06` 不得用人工操作判定。WP-06 完成时，研发必须提交 `test/fixtures/replays/baseline_clear_v1.json`，固定为 `seed=0x4E454F4E0001`、`contentVersion=2.0.4-release` 和正式 `素材/manifest.json` 的 SHA-256，并记录每个逻辑帧的 `InputFrame`、选卡 ID、风险门选项和期望的 `RunEnded` 摘要。该文件由技术负责人通过一次后冻结并纳入版本控制；以后每次构建都回放它，要求 180 秒前胜利、HP 从未受伤、事件摘要 hash 一致。素材或内容版本变更时，回放必须显式更新版本、manifest hash 和对应变更说明；版本或 hash 不匹配时不得执行旧回放并不得将其结果计为通过。

## 6. 最终验收规则

P0 任何一项失败即阻断开发里程碑；P1 失败可只在技术负责人记录风险、制定修复版本后进入内部测试，不能标记正式发布。所有 `AC-01` 至 `AC-09`、正式素材许可、Web 回归和性能目标通过后，v2.0 才可验收完成。
