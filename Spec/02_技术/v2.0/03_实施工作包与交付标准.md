# 03｜实施工作包与交付标准

## 1. 实施总原则

每个工作包合入前必须：通过格式化、静态分析、现有测试与新增测试；无未使用资源；无产品规则硬编码；更新该工作包要求的测试。工作包完成不等于视觉最终素材到位，允许使用带 Asset ID 的占位资源，但不得跳过资源查表、事件或状态逻辑。

## 3. 建议提交边界

- 一个提交只能解决一个工作包中的一个可验证切片，例如“固定时钟与暂停”，而不是“所有核心系统”。
- 任何配置新增先提交 Schema/validator/fixture，再提交运行时消费逻辑。
- 任何新 `DomainEvent` 必须同时提交：事件定义、至少一个生产者、至少一个表现/测试消费者。
- 不允许“先把所有逻辑塞入 `WarshipGame`，以后再拆”；`WarshipGame` 只允许作为 Runtime/Flame 桥。

## 4. 代码审查检查表

| 类别 | 必须检查 |
| --- | --- |
| 规则 | 是否与 v2.0 内容表一一对应？是否有隐藏硬编码？ |
| 确定性 | 遍历是否排序？随机是否只来自 Run PRNG？时间是否只来自逻辑时钟？ |
| 状态 | 停止/暂停时是否冻结所有逻辑 Timer？是否会重复发事件？ |
| 生命周期 | Component、listener、音频、指针和异步加载是否都有释放/取消路径？ |
| 性能 | 是否分配临时集合、全量碰撞、频繁解码、无上限粒子/音频？ |
| 可测试性 | 是否可注入时钟、随机、内容、存档和音频 fake？ |
| Web | 是否引用桌面专属 API？失焦、用户手势音频、离线是否受测？ |
| 可读性 | 是否使用 Asset ID/文案 key，而非显示字符串或资源路径？ |

## 5. Definition of Done

一个功能可标记完成仅当：产品基线对应条目实现；至少一条成功与一条失败/边界自动化测试；HUD/音频/资源事件完整；Web 与暂停路径不残留状态；可观察日志可定位失败；代码审查通过；相关 `AC-*` 用例更新。测试失败、临时硬编码、没有资源回退、仅桌面输入可用均不能进入完成状态。

## 6. 变更管理

产品基线以外的需求进入变更单，不得以“顺手实现”进入 v2.0。只影响技术内部、且不改变可见行为、数值、性能预算或数据兼容性的重构，可由技术负责人决定；其余修改必须更新产品基线、内容版本、测试用例及素材映射。
