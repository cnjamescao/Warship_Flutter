## 问题清单

### P1 — 同一敌人在同一帧被多颗子弹命中时会被重复计分

- 位置：`lib/game/warship_game.dart:423-455`
- 原因：命中扫描只保证“一颗子弹只命中一个敌人”，却没有排除已经加入 `aliensToRemove` 的敌人。两颗重叠的子弹可以各自把同一个敌人加入列表；随后分数用列表长度计算。
- 影响：一个实际只移除一次的敌人可能获得 100 分或更多；同一组件也会被重复调用移除。
- 建议：把待删除集合改为 `Set<AlienEnemy>` / `Set<Bullet>`，或在内层循环跳过已标记的敌人；以**唯一移除的敌人数量**结算分数。补充“多颗子弹命中同一敌人仅得 50 分”的回归测试。

### P1 — 窄窗口会产生无效边界，可能导致运行时异常或不可玩布局

- 位置：`lib/game/warship_game.dart:326-335`、`531-555`
- 原因：当画布宽度小于飞船宽度 64px 时，`_ship.x.clamp(0.0, size.x - _ship.width)` 的上限小于下限。`_resetShip()` 也会产生负 x；舰队算法虽强制至少一列/行，却仍可能将 48px 敌人放到比它更小的画布外。
- 影响：用户缩小 macOS 窗口时可能抛出异常，或出现飞船/敌人越界与异常反向。
- 建议：定义最小逻辑画布尺寸（推荐固定虚拟分辨率后等比缩放），或在更新前使用 `max(0, size.x - _ship.width)` 作为边界，并在小于可玩尺寸时暂停游戏、显示“窗口过小”。为 1px、64px、常规尺寸加入 resize 测试。

### P1 — 输入状态不能正确处理同一动作的两个按键，失焦后也可能“粘键”

- 位置：`lib/game/warship_game.dart:267-298`
- 原因：`A` 与 `←` 共用一个布尔值。两个键同时按下后，先松开其中任意一个就会把 `_leftPressed` 置为 `false`，尽管另一个仍按住；传入的 `keysPressed` 集合未被使用。窗口失焦时未必能收到 `KeyUpEvent`，同样会保留旧状态。
- 影响：桌面端操控偶发中断或持续移动/射击，尤其在切换窗口时。
- 建议：以 `keysPressed` 计算每个动作（例如任一左键仍在集合中即左移），并在焦点失去、暂停、游戏结束与销毁时清空输入。增加别名组合与失焦复位测试。

### P1 — 调整窗口后游戏世界不重新布局，舰队会越界或在边界反复掉落

- 位置：`lib/game/warship_game.dart:183-213`、`387-413`
- 原因：`onGameResize` 只调整背景；飞船、子弹和敌人仍使用旧绝对坐标。随后任意越界敌人每帧都触发换向和下移。
- 影响：这是现有 macOS 唯一目标平台上的常规用户操作，窗口缩小后游戏规则可能明显失真并快速掉命。
- 建议：优先采用固定逻辑画布 + viewport 缩放；备选方案是 resize 时暂停，按比例约束飞船/子弹位置并重建或重排舰队。把“resize 后全体对象在边界内、不会连续下移”设为验收标准。

### P2 — 游戏实例及其 `ValueNotifier` 没有明确释放，延后 UI 回调也没有生命周期保护

- 位置：`lib/game/warship_game.dart:590-617`、`lib/main.dart:114-125`
- 原因：四个 `ValueNotifier` 从未 `dispose()`；`_GameScreenState` 没有 `dispose()`。`_markUiDirty()` 注册的 post-frame 回调也可能在宿主移除后执行。
- 影响：单屏常驻时影响很小，但导航、测试反复挂载或未来多局/多页结构下会留下监听器与延后回调，增加泄漏和“已释放对象仍更新”的风险。
- 建议：明确 `WarshipGame.dispose()` / `close()` 的所有权，取消或守卫已排队的同步，并由 `_GameScreenState.dispose()` 调用。不要由多个层级重复释放同一资源。

### P2 — 舰队触边后不回夹位置；低帧率或未来高速度下会出现可见越界

- 位置：`lib/game/warship_game.dart:392-413`
- 原因：敌人先移动，再仅反转方向并下移；未把本帧越过的 x 坐标夹回合法范围。速度越高或 `dt` 越大，越界距离越大。
- 影响：后期波次、窗口恢复或卡顿后，舰队可能明显穿出屏幕并使下一次边界判断不稳定。
- 建议：在翻转方向前计算舰队边界与可用位移，或在触边后整体平移回边界；同时为速度设置上限。添加大 `dt` 与高波次测试。

### P2 — UI 同步依赖 Flutter 的 post-frame 回调，时序比游戏状态晚一拍且测试难以确定

- 位置：`lib/game/warship_game.dart:588-617`
- 原因：游戏状态先写入私有字段，通知器在 Flutter 帧末才同步；Flame 的 update 与 Flutter frame 并不是同一个领域时钟。
- 影响：界面、测试和外部消费者无法在状态改变的同一逻辑点可靠观察到新值，且必须额外 `pump()`；延迟回调还加大了上项生命周期风险。
- 建议：对罕见状态/计分变更直接同步 notifier；如果确实需要批处理，抽出受测试的状态模型并采用明确的 flush 生命周期，而非依赖 WidgetsBinding。

### P2 — 回归测试以“500ms 后不崩溃”为主，覆盖不到核心规则正确性

- 位置：`test/widget_test.dart:6-25`、`test/game_flow_test.dart:23-145`
- 原因：资源加载采用固定 500ms 等待，属于环境相关的时间假设；输入、射击、计分测试只断言无异常或状态仍为 `playing`，没有断言位置、子弹数量、唯一得分、边界或 UI 文案。
- 影响：本次发现的重复计分、窄窗口、别名按键问题可在测试全绿时存在；较慢 CI 也可能出现偶发失败。
- 建议：暴露最小的只读游戏查询接口，或把碰撞/规则抽至纯 Dart 对象；等待 Flame 的加载完成信号，而不是 sleep；按“行为 + 结果”断言覆盖本反馈的 P1 问题。

### P3 — `WarshipGame` 集中了承载、输入、规则、碰撞、UI 通知与资源生命周期，扩展成本会快速上升

- 位置：`lib/game/warship_game.dart:55-617`
- 影响：目前规模尚可维护；一旦加入暂停、音效、敌方子弹、道具、持久化或多敌人类型，单类会成为冲突和回归热点。
- 建议：先做轻量分层，不必过度抽象：`GameSession`（状态/计分）、`InputController`、`FleetController`、`CollisionResolver`，Flame 组件保留表现与局部行为。将数值配置集中为不可变配置对象。

### P3 — 产品与工程文档不足，现有规格有少量不准确或实现细节与目标混写

- 位置：`README.md:1-3`、`Spec/Warship产品设计.md`
- 影响：新贡献者无法从 README 获得运行、控制、平台限制和测试说明；规格将“当前实现”“已知缺陷”“下一步产品目标”混在一起，难以作为验收基线。
- 建议：保留原始 as-built 文档作历史基线，使用本次新增的审阅修订版明确 `已实现 / 未实现 / 提议`。README 至少写明 Flutter 版本、运行/测试命令、控制方式、macOS 限制和规格链接。

## 建议实施顺序

1. 修复唯一命中计分、输入状态和最小画布/resize（上述 P1）。
2. 为 P1 情形补确定性测试，再重构 UI 状态同步和资源释放。
3. 以固定逻辑画布为基础推进暂停、最高分持久化、音效与难度曲线。
4. 在功能稳定后拆分 `WarshipGame`，并补 README 与 CI。
