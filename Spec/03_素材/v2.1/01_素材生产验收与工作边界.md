# v2.1 素材生产、验收与工作边界

| 项目 | 规定 |
| --- | --- |
| 状态 | **当前生效 v2.1 素材工作规则；v2.0 仅作为保留资源基线** |
| 适用对象 | 项目负责人、产品、技术架构、UI/TA、音频、QA、一线研发 |
| 核心原则 | 素材必须先真实生成并逐项审查；“文件存在/命名正确/哈希不同”不等于素材可用 |
| 生效时点 | 即刻适用；研发只可按 v2.1 清单接入，素材文件与文档不得自行修改 |

## 1. 对上一阶段问题的纠正

上一阶段曾出现“资源文件存在但实际是占位、重复或静态替代”的情况，造成玩家把素材问题误判为程序问题，也让研发进行了不必要的运行时排查。**v2.1 禁止以任何形式重复这种交付。**

以下行为均不允许被标记为“已完成素材”：

- 用空白图、通用几何图、同一张图片换名、同一图片换色、回退剪影或静态截图替代应有素材；
- 将单帧静态图以长时间停留冒充动效；
- 只检查 Asset ID、路径、尺寸、哈希或文件数量，而未检查实际画面/声音语义；
- 未生成实际文件即称“已交付”，或把“后续由研发替换”写成素材完成；
- 用代码 Canvas/程序图形绕过本应交付的正式美术或音频资源，除非产品与素材规范明确批准该资源为程序化效果。

## 2. 职责边界（保持上一阶段原则）

| 角色 | 必须负责 | 不得越界 |
| --- | --- | --- |
| 项目负责人 / 产品 / 架构验收 | 确认玩法、验收口径、素材清单完整性、技术文档边界、最终 Code Review 与交叉核验 | 不以“看起来差不多”替代素材实际审查；不把未确认提案写入现行技术规范 |
| 素材负责人（本角色） | 按确认清单**实际生成**图形、动效、音频及源文件；逐项进行语义和质量验收；维护素材状态与证据 | 不交付占位、重复替代或未经审查的资源；不要求一线研发猜测素材含义 |
| 一线研发 | 仅按已确认的技术协议、manifest、Asset ID 和接入说明编写代码与测试；报告素材加载/表现异常 | 不改写素材本体、不自制替代素材、不用程序图形掩盖素材缺失 |
| QA | 在真实 Release 环境验证素材、动效、音效和交互的实际表现，保存截图/录屏/设备信息 | 不把 Debug 截图或文件名检查当作发布视觉验收 |

## 3. v2.1 素材生产流程（必须按顺序）

~~~text
确认产品需求
  → 编制完整 Asset 清单与状态矩阵
  → 为每个 Asset 实际生成源文件与运行时文件
  → 单项视觉/听觉审查
  → 动效时序与差异帧审查
  → 重复/占位/路由预检
  → 素材负责人签署“可接入”
  → 才允许研发接入 manifest 与代码
  → Release 实机复验
~~~

任何一步失败，资源状态只能是“待生成”或“返工中”，不得写成完成。

## 4. 素材清单的强制字段

v2.1 每一个 Asset（包括 HUD、弹道、特效、动效帧、奖章、音频和可访问性叠层）必须有独立记录；“一个组名”或“后续补齐”不算记录。

| 字段 | 图形 / 动效 | 音频 |
| --- | --- | --- |
| 稳定 Asset ID | 必填，不复用语义 | 必填，不复用 cue 语义 |
| 玩家可见目的 | 必填：它让玩家看懂什么 | 必填：它让玩家听懂什么 |
| 触发与结束 | 必填：事件、条件、层级、结束规则 | 必填：事件、总线、停止/合并规则 |
| 实际文件 | 源文件、运行时文件、尺寸、透明/色彩空间 | 母带、运行时文件、时长、编码、响度 |
| 动效信息 | 帧数、帧率/时间曲线、锚点、混合方式、并发上限、降级 | 变体、循环点、最大并发、重播间隔 |
| 区分依据 | 与任何近似资源相比的形状/运动/语义差异 | 与任何近似 cue 相比的节奏/音色/用途差异 |
| 验收证据 | 逐项缩略图/序列预览、审查结论 | 波形/频谱/试听结论、审查结论 |

## 5. “真实素材”验收规则

### 5.1 图形与静态 UI

每个图形资源必须同时通过：

1. **文件真实性**：源文件与运行时导出真实存在、可解码、透明边缘/尺寸/锚点符合清单。
2. **视觉语义审查**：素材负责人实际查看图像本身，确认它画出的对象、轮廓、颜色和状态与清单一致。
3. **差异审查**：与同类资源逐项比较；不同游戏语义不能共用同一画面、同一主体剪影或仅换色的复制品。
4. **占位排除**：不得是空白、棋盘、测试图、通用几何、回退剪影、文字标签或不相干 UI。
5. **运行时可读性**：在目标尺寸下能与玩家/敌人/危险区区分；灰阶或低动效场景下仍保留必要形状信息。

哈希、感知重复检测、alpha 覆盖率和尺寸检查只能作为筛查工具；**不能替代第 2、3、4 项的人眼审查。**

### 5.2 动效与特效

动效不是“同一张图显示一段时间”。每个动效必须同时提供：

- 至少 3 个有意义的阶段（例如出现/冲击、峰值、收束/消失），相邻帧或参数必须产生可见变化；
- 时间线预览，明确总时长、帧率/曲线、循环或一次性播放、何时停止；
- 机体受击、低血、命中、击毁等状态的分层关系，证明不会遮住机体或危险信息；
- 高并发下的合并、最大实例数与低性能降级；降级可以减少碎片但不能退化成占位静图或丢失关键状态；
- 一段实际播放预览（序列帧/GIF/视频或引擎预览）和逐帧审查记录。

### 5.3 音频

每条音频必须实际生成可播放文件；不得以静音、通用 beep 或同一文件冒充不同语义。验收必须检查试听、时长、波形/频谱、响度、循环点、总线、最大并发和与画面事件的对应关系。相近音效必须能从音色、节奏、包络或触发用途区分。

## 6. 两阶段验收与状态定义

| 状态 | 含义 | 是否可由研发接入 |
| --- | --- | --- |
| `planned` | 已确认需求，尚未生成文件 | 否 |
| `generated` | 已生成文件，未完成逐项审查 | 否 |
| `asset-reviewed` | 已完成人眼/试听/动效审查与占位排除 | 可进入 manifest 接入准备 |
| `integration-reviewed` | 在真实加载路径中确认 Asset ID、状态、层级、时序正确 | 可进入 Release 验收 |
| `release-accepted` | 真实 Release 设备/浏览器画面和声音验收通过 | 是 |
| `rejected` | 占位、重复、语义不符、损坏或不可读 | 否，必须返工 |

只有 `asset-reviewed` 以后才允许一线研发接入；只有 `release-accepted` 才能从发布遗留清单关闭。

## 7. v2.1 首批素材验收重点

本轮确认的玩法所需素材族已经逐条登记；完整数量、Asset ID、帧表、hash 和接入动作以 [素材清单与制作规范](02_素材清单与制作规范.md) 为准：

| 素材族 | 最低实际交付 |
| --- | --- |
| 战机状态动效 | 护盾受击、HP 受击、低血、濒危、命中、敌人击毁的分层动效及低动效版本 |
| 自动结果反馈【v2.1-R2】 | 自动强化、补给、悬赏、超载四种无文字结果徽记；战斗内禁止用卡片、文字、边框或占位图替代，完整说明仅供语义/历史使用 |
| 弹道形态 | Prism / Arc / Plasma / Needle / Missile 的弹体、尾迹、命中、可选爆裂和对应音频 |
| 清场结算 | 扇区清空提示、目标状态文案承载、短音画确认 |
| 三档奖章 | Gold / Silver / Bronze 各自独立的源图、运行时素材、入场动效、静态降级和 cue |

## 8. 技术、素材与验收文档隔离规则

1. 当前 v2.1 生效通路为 `Spec/01_产品/v2.1/`、`Spec/02_技术/v2.1/`、`Spec/03_素材/v2.1/` 与根目录 `素材/v2.1/`；v2.0 只用于明确保留项和历史追溯。
2. 研发必须按产品冻结表、代码改造蓝图和本素材清单实施；不得自行增删 Asset ID、数值、接口、测试数量或状态。
3. 研发可据此直接修改业务代码，但不得替换、重绘、改名或伪造 v2.1 源素材；素材问题按清单状态和验收门禁报告。
4. 每个工作包合入前，项目负责人须完成产品一致性、技术实现、素材完整性、测试可验收性和 Code Review 检查。

## 9. 项目负责人验收承诺

后续 v2.1 素材交付，我将只在以下条件全部满足时报告“完成”：

1. 清单中的每一个应交付资源都有实际文件，而不是占位或待补说明；
2. 我已实际查看每张图、每段动效预览，并试听每条音频；
3. 我已检查资源之间的视觉/听觉语义差异，不只检查名称和哈希；
4. 我已记录每项的状态、证据和未通过原因；
5. 研发真实接入后，QA/Release 复验没有发现资源回退、遮挡、错误路由或占位显示。

任一条件未满足，我将明确报告“未完成”，而不会以“已检查通过”代替实际交付。
