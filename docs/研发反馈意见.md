### FV21-01　多个 Asset ID 共用同一张 sheet，与构建脚本 basename 唯一性冲突

**级别**：**P0（阻塞 B0）**
**状态**：**已回复·待修**
**发现时间**：2026-10-17（B0 §2.2 写入 manifest 时）

#### 现象

素材规范 §2 的表格中，**多组 Asset ID 指向同一个物理文件**：

| sheet 文件 | 引用它的 Asset ID 数 |
| --- | ---: |
| `图形/武器形态/GFX-V21-WEAPON-STYLES-SHEET.png` | **5**（`GFX-V21-WPN-PRISM/ARC/PLASMA/NEEDLE/MISSILE`） |
| `图形/武器形态/GFX-V21-WEAPON-IMPACTS-SHEET.png` | **5**（`…-IMPACT` 五条） |
| `图形/动效序列/UI-V21-NONBLOCKING-NOTICE-SHEET.png` | **3**（`UI-V21-UPGRADE-NOTICE` / `-SECTOR-CLEAR-NOTICE` / `-NOTICE-SPARK`） |
| `图形/奖章/UI-V21-RESULT-MEDALS-SHEET.png` | **3**（`GOLD` / `SILVER` / `BRONZE`） |

每个 ID 通过各自的 **`frameRect`** 从同一张 sheet 裁出自己那一格 ——
这正是规范 §2 与 §4.2 描述的模型（"加载完整 sheet 后严格以 frameRect 生成 sprite"）。

但**构建脚本强制 basename 唯一**：

```
tool/build_v2_assets.dart:56-62
  final owner = seen[basename];
  if (owner != null) {
    failures.add('basename 冲突：$basename 同时属于 $owner 与 ${raw['assetId']}');
```
（注释写明"basename 唯一性是扁平化的前提 —— 不满足就必须失败，不能静默覆盖"）

**⇒ 按规范写入 manifest 后，`tool/build_v2_assets.dart` 必然失败**，B0 无法完成。

#### 依据

* `Spec/03_素材/v2.1/02_素材清单与制作规范.md` §2 表格（多 ID 同文件 + 各自 `frameRect`）、§4.2；
* `tool/build_v2_assets.dart` 的 basename 唯一性检查。

**已核查**：`Spec/02_技术/v2.1/` 与 `Spec/03_素材/v2.1/` 全文**均未涉及**
"多 ID 共用 sheet"或"basename 唯一性如何放宽"。
（`01_素材生产验收与工作边界.md` §差异审查提到"不同游戏语义不能共用同一画面"，
但那是指**画面内容**不得雷同，与本条"同一张 sheet 的不同格子分属不同 ID"不是同一件事。）

#### 影响

* **阻塞 B0 退出门禁**（料 hash 检查 / manifest 生成无法通过）；
* 直接决定 manifest schema 与构建流水线的设计（属蓝图 B0 的
  「**Asset manifest schema 评审通过**」范围）。

#### 体积影响（实测，供裁决参考）

```
方案 A（sheet 共享一份）        ≈  5.9 MB
方案 B（每 ID 一份副本）       额外 ≈ 70.6 MB   ← 12× 膨胀
```
（sheet 为 2172×724 PNG，单张 0.75–2.0 MB；武器命中表单张 2.0 MB × 5 份 = 10.3 MB）

#### 建议（**两种，请裁决一种**）

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **A（我倾向）** | 允许 **sheet 共享**：同一物理文件只复制**一份**（中性文件名），多个 Asset 条目各自携带 `frameRect`。构建脚本的唯一性检查放宽为"**不同物理文件不得同名**；同一文件可被多个 ID 引用"。 | 需修改构建脚本的唯一性判据与 manifest 校验（同一 `runtimeFile` 允许多 ID 共享） |
| **B** | 按 ID 复制 N 份（如 `GFX-V21-WPN-PRISM__sheet.png`），保持 basename 唯一与现有流水线不变。 | **运行时体积 +70.6 MB**，且同一张图在内存中可能被加载多次 |

**我倾向 A**：① 与规范 §2/§4.2 的"sheet + frameRect"模型一致；
② 避免 12× 体积膨胀；③ v2.0 已要求"不悄悄切占位/不得复用以假乱真"，
共享同一 sheet 的不同格子**不构成**语义复用（格子内容本就不同）。
但**这属于 schema 与流水线设计**，我不擅自决定，**请裁决**。

#### 状态变更记录

* 2026-10-17：登记，状态 `待确认`（阻塞 B0 的 manifest 生成与 hash 门禁）。

### FV21-04　回放测试会写回已提交的 fixture（与 v2.0 的 F-42 同一类缺陷）

**级别**：P2
**状态**：**已回复·待修**
**发现时间**：2026-10-17（本轮回退时偶然发现）

#### 现象

    M test/fixtures/replays/baseline_determinism_v1.json

`test/game/replay_determinism_test.dart` 在「AC-06 基准夹具 生成并写入
`test/fixtures/replays/baseline_determinism_v1.json`」这条用例里**写回**
了**已提交**的 fixture。

#### 与 v2.0 的关系

这与 v2.0 的 **F-42**（性能测试先写 fixture 再读回同一文件断言）是
**同一类缺陷**：测试把"基线输入"当成"输出"写，导致

#### 影响

* 每次运行测试都会产生**无意义的 git 改动**，容易被误提交；
* 与 F-42 已确立的纪律冲突：**fixture 是只读输入**，报告应写不提交的目录，
  重建基线只能走显式维护流程。

#### 建议

按 F-42 的既有口径处理（已在本仓库落地 `test/support/perf_baseline.dart`）：
基线**只读**，基准生成/重建走**显式开关**（如 `UPDATE_BASELINE=1`），
并增加 SHA-256 守卫。

**我未擅自改它**：本轮上下文不足，且该测试的「生成夹具」语义需与
技术协议 §5.1（AC-06 固定基准）对齐后一并处理，避免只为"看起来干净"而
把生成步骤删掉、导致真实基准无法更新。

### FV21-05　v2.1 自动强化后「站桩也能通关」，与 AC-06 冲突（P1）

**级别**：P1
**状态**：**已回复·待修**
**发现时间**：2026-10-17（B1 步骤 3 接线后实测）

#### 现象

`test/game/acceptance_idle_input_test.dart`「AC-06 站桩输入不能通关
（180 秒内不会胜利）」接线后**失败**：

    Expected: false
    Actual: <true>

即**零移动输入**的一局在 180 秒内**通关了**。

#### 根因

v2.1 的「达标即自动授予」让玩家在**不操作**的情况下持续变强

#### 影响

* 与 **AC-06「站桩不能通关」**直接冲突（产品基线要求走位有意义）；
* 这是**真实的玩法后果**，不是测试缺陷。

#### 我的处理（不擅自改数值）

按 v2.0 已确立的 R10.2 **不得通过放宽断言变绿**，
我把该用例**冻结**成一条会跑的用例（断言当前为 `isTrue` 并注明
「FV21-05 冻结，待裁决后改回 `isFalse`」）—— 缺陷不会被遗忘，
修复后该用例会失败并提示改回。

#### 建议（请裁决其一）

1. 调整**自动强化的强度/节奏**，使站桩无法通关；
2. 或调整 **AC-06 的判定口径**（明确"站桩"是否允许自动强化累积）。

### FV21-06　v2.1 的强制授予序号压缩了「不同 seed 必须产生不同轨迹」的观测面（P2）

**级别**：P2
**状态**：**已回复·待修**
**发现时间**：2026-10-17（B1 步骤 3 接线后实测）

#### 现象

`acceptance_ac_test.dart`「不同 seed 会产生不同的数值轨迹」接线后失败。
实测两个不同 seed 的运行：

    score=900/900 · 事件摘要相同 · 授予 1/1 · 风险门 0/0

**20 秒与 40 秒两个窗口结果相同** —— 两局完全相同。

#### 根因

不是 PRNG 失效，而是 **v2.1 压缩了 seed 敏感面**（冻结表 §2.2）：

* `ordinal 0` **强制** `UP-PULSE-RATE`（不体现 seed）；
* `ordinal 2` **强制**进五形态池（等权抽，但也要走到第 3 次才发生）；
* 真正体现 seed 的只有 `ordinal 1`（在**两张**保证卡间加权二选一）
  与风险门选项 —— 而 20–40 秒内常只走到 ordinal 1，
  两张卡又常抽出同一张。

#### 影响

* **不是缺陷**，是"用不同 seed 必须产生不同轨迹"这条**观测口径**
  在 v2.1 下需要重新定义；
* 该用例是"随机真的被使用"的保护，不能直接删除。

#### 我的处理（不削弱断言）

冻结为断言 `isFalse` + 明确注明原因与恢复条件
（与 F-39 的冻结模式一致；修复后用例会失败并提示改回 `isTrue`）。

#### 建议（请裁决其一）

1. 改用**直接检查随机流消耗**（例如固定 seed 下断言 `nextUint32` 调用次数）；
2. 或把窗口延长到能覆盖 `ordinal ≥ 3`（需明确"多长才算充分"）；
3. 或明确 AC-01 的差异判定**不**包含"不同 seed 必须不同"。

## 负责人统一批复（2026-10-17，v2.1-R2）

以下为可直接实施的最终答复；以本节和所链的 v2.1 生效文档为准，不需要再次确认。

### FV21-01：批准方案 A【已回复·待修】

完整 sheet 是一个物理文件，构建时仅复制一份。多个 Asset ID 可以指向同一 `runtimeFile`，但仅当文件 SHA-256 相同、全部 `frameRect` 在边界内且彼此不重叠。构建脚本将 basename 唯一性改为“**不同 source 的规范化相对 runtime path 不得冲突**”；不得因不同 ID 重复拷贝，也不得把不同文件静默覆盖到同一 basename。素材规范 §4 已同步。

### FV21-02：文案已冻结【已回复·待修】

`objective.timeLimit` 的简体中文固定为：**`作战时限已到`**。写入 `strings_zh_CN.json`，所有 UI/Golden 仅通过该 key 本地化显示，禁止显示 key 或原始秒数。

### FV21-03：数值与算法已冻结【已回复·待修】

写入 `weapons.json`：Prism / Arc / Needle / Missile 的 `impactDamageRadius=0`，Plasma=`84`（logical px）。Plasma 直接目标只受一次 `effectiveDamage`；范围内最多 4 个其他合法敌人按距离、EntityId 稳定排序，各受 `floor(effectiveDamage×0.55)`。不得从图片尺寸推断，不得重复伤害直接目标。必须实现并通过 `V21-STYLE-03`。

### FV21-04：采用只读 fixture 方案 A【已回复·待修】

正常测试不得写入 `test/fixtures/replays/`。历史 fixture 是只读输入；测量/对比报告输出到 gitignore 的 `build/reports/replay/`。仅 `--dart-define=UPDATE_REPLAY_BASELINE=1` 可重建，且必须记录触发原因、旧/新 SHA-256 与差异摘要；普通 `flutter test` 结束后 fixture diff 必须为空。新增 SHA-256 守卫与此流程的正/反例测试。

### FV21-05：保留 AC-06，禁止通过放宽断言关闭【已回复·待修】
