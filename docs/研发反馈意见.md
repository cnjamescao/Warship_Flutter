## F-01 设置/简报/HUD 文案缺少本地化 key

**现象**：`lib/app/v2_app_flow.dart` 里下列展示文案是**硬编码**的，
而 `assets/config/v2/strings_zh_CN.json` 中**没有对应 key**：

| 位置 | 硬编码文案 |
| --- | --- |
| 首页 | 「最高分 {n}」「最快通关 {n} 秒」 |
| 首页 | 「WASD / 方向键移动 · 空格或 Shift 冲刺 · Esc 暂停」 |
| 设置页 | 「设置」「背景音乐」「音效」「减少动效」 |
| 设置页 | 「只降低非关键动效，预警仍然清晰」「触感反馈」「返回」 |
| 简报页 | 「作战简报」「坚持 150 秒，击败守门者 Aegis」等 |
| HUD | 「生命」「护盾」等（部分 key 已存在，需逐项核对） |
| **升级草案** | 卡片标题显示 **Asset ID 原文**（如 `UP-PULSE-RATE`）、
  描述显示 **未解析的 key**（如 `up.pulseRate.desc`） |

**依据**：产品设计文档 §8「所有展示文本使用本地化 key，
**不在玩法逻辑中硬编码**」。

**研发已自行修复的部分**（这些 key 存在）：
* 首页标题 → `app.title`（按冒号拆主/副标题，版式不变）
* 首页按钮 → `home.start` / `home.settings`
* 结算页 → `result.victory` / `result.defeat` / `result.score` /
  `result.time` / `result.best` / `result.tier.*`

**请求**：在 `strings_zh_CN.json` 补齐上表所需 key。
**研发不擅自增删内容** —— 文案属于素材/产品侧产物。

> **升级卡的情况更严重**：草案里显示的是 `UP-PULSE-RATE`（Asset ID 原文）
> 和 `up.pulseRate.desc`（未解析的 key 字面量）。这不是"没本地化"，
> 而是**玩家会直接看到内部标识符**。文案位置是明确的，
> `upgrades.json` 里每张卡有 `id` 与 `descriptionKey`，缺的是
> `strings_zh_CN.json` 里的对应条目。

## F-03 结算奖牌算法：产品基线 §8 vs 技术协议 §3.1（已裁决，待追认）

**冲突原文**：
* 产品基线 §8：「胜利为 Gold；Boss HP ≥35% 的失败为 Silver；其余为 Bronze。」
* 技术协议 §3.1：「gold；失败但曾进入 Boss P3（`bossHpRatio < 0.35`）
  silver；失败且存活 ≥120 秒 bronze；其余 `none`。」

**裁决**：按交付清单 §8「产品基线 → 技术协议 → …」，
**产品基线优先**。实现为：

| 情形 | 结果 |
| --- | --- |
| 胜利 | `gold` |
| 失败且把 Boss 打进 P3（`< 0.35`） | `silver` |
| 其余失败 | `bronze` |
| — | **不产生 `none`** |

**两处需要追认的判断**（研发已记录理由，但建议产品确认）：
1. **阈值方向**。产品基线只写「Boss HP ≥35%」没说方向。按字面读
   「剩余 HP ≥35% 才 Silver」会**打得越差奖牌越好**，与它自己的
   档位排序（Silver > Bronze）矛盾。故以技术协议的显式算法解释它。
2. **`none` 的存废**。技术协议给 `none`、产品基线说「其余为 Bronze」，
   直接冲突 → 按 §8 判产品基线优先，故不产生 `none`。

**若产品侧本意是保留 `none`**（例如"开局即失败不该拿铜牌"），
请明确，研发改一处即可。

## F-04 低血/低护盾提示的最短间隔与 §7.5 不符

产品设计 §7.5 的音频必须项：

与 §7.5 的"避免反复跳变"意图不符。
**请求**：素材侧把这两个 cue 的 `minRetriggerMs` 改为 `8000`。

## F-05 条件绑定无法被任何适配器产出（16 项）

`lib/game/infrastructure/audio_director.dart` 的 `conditionalParamsOf`
是 Domain 事件 → 条件参数的**唯一适配器**，它只覆盖 36 个事件里的 19 个。
凡没有分支的事件，参数 map 为空，**其带条件的绑定永远匹配不上**。
共 16 项，分三类：

1. **适配器完全没有该事件的分支**（7 项）：
   `UiCommand` 的 `command`、`EnemyDefenseStateChanged`、
   `EnemyVitalStateChanged`、`RiskOptionStateChanged`、
   `WeaponSustainStarted/Stopped` 的 `weaponId`。
   → 后两个直接关系**激光循环音的起停**（防叠音）。
2. **有分支但键名不一致**（3 项）：
   * `PlayerDamaged` 适配器产 `hpDamage`/`shieldDamage`，
     绑定却要 `hpRatio`/`shieldRatio`
   * `RiskGateOpened` 适配器产 `gateId`，绑定要 `optionId`
3. **适配器不产出的状态类键**（6 项）：
   `availability`、`frontShieldActive`、`state`、`controlId`、`resultTier`。

**已做的**：这 16 项已冻结为已知集合并加断言（
`test/game/acceptance_visual_states_test.dart`），防止继续扩大。
**待定**：需要确认每一项是"该事件本该有分支而漏了"还是"绑定写错了
事件名/条件键"。**这属于内容与协议的交叉问题，研发不擅自改动素材绑定。**

## F-07 AC-04「无不可躲避 Boss 循环」的模型精度（**已做联合分析**）

**已补上联合可解性分析**（2026-10-14）：在 `acceptance_fairness_test.dart`
新增「招式序列的联合可解性（贪心模型）」，对 `boss_aegis.json` 的
`attackOrder`（fan → charge → ring → summon → laser，环形）检查
**任意相邻两招**：从"前招安全区的任意位置"出发，能否在"后招的预警时长"
内抵达"后招的安全区"。

**检查报出一处**：`boss_charge → boss_ring` 最坏需移动 884 px，
而 0.90 s 内只有 666 px。

**但研发不认为这是公平性缺陷** —— 这是**模型的保守性**导致的：
`DangerShape` 不随时间移动，于是冲锋被建模成一个**固定不动的 180° 扇区**，
而真实冲锋会移动、冲过去之后身后就是安全的。因此那一对的距离被高估。

**处理**：该情形已作为"已知模型保守情形"登记在用例里并写明理由，
**不宣称它是缺陷**。

**仍待你确认**（与之前一致）：AC-04 要验收到什么严格程度？
* (A) 当前水平：单招可躲 + 相邻招式连通（模型保守，可能低估公平性）；
* (B) 让模型支持"随时间移动的危险区"，给出更准的结论（工作量较大）；
* (C) 只保留单招验证，不做序列分析。

研发建议 (A) —— 它已能拦住"某一招根本躲不掉"这类硬问题，
而 (B) 的收益主要是减少假警报。

## F-16 Golden 无法在 CI 的 macOS runner 上比对（**已从 CI 移除**）

**实测结论（2026-10-14）**：本机 macOS 生成的 6 张基线，
在 CI 的 **macos-latest** runner 上**全部失败**。
说明「macOS」并不等于一个足够稳定的比对平台 ——
系统版本、无 GPU 的软件光栅路径都会改变像素。

**处理**：已把 Golden 步骤**从 CI 移除**，改列为**本地/发布前门禁**
（`flutter test --tags golden`），避免长期挂着一条必然失败的流水线。

**这是研发的失误，如实记录**：我在加 CI 步骤前**已经识别出这个风险**
（规范写的是"稳定平台"，而 CI 与本机不是同一实例），却仍然先加了步骤，
结果真的把 macOS job 弄红了一次。

**要在 CI 落地 Golden 的可行路径**（需你选择）：
1. 加一个**手动触发**的工作流，在 runner 上用 `--update-goldens` 生成基线
   并作为 artifact 下载，提交后再由 CI 比对（基线归属 runner，而非开发机）；
2. 或固定一个**容器化/固定镜像**的渲染环境；
3. 或接受 Golden 只作为**发布前人工执行**的门禁，不进 CI。

研发倾向 1，但这会影响 CI 时长与流程，故请示。

## F-15 音效/音乐独立音量（**已修复**，记录在此以免重犯）

产品设计 §8 要求「音效/音乐**独立**音量」。此前音频层的实现是：

    _audio.setMuted(!_settings.sfxEnabled && !_settings.musicEnabled);

**只有两个开关都关才会静音** —— "关掉音乐、留着音效"时两者都还在响，
两个开关等于只有一个在起作用，且是错的那个。

**研发已修复**：`AudioService` 改为按总线独立判定
（音乐总线看 `musicEnabled`，音效/UI/预警看 `sfxEnabled`），
关闭总线时立刻停掉该总线的循环音。新增 7 个用例守住语义，
其中一条专门覆盖"只关音效、留着音乐"这个旧实现出错的情形。

**教训**：把两个布尔量用 `&&` 合成一个开关，是"看起来实现了、
实际语义错了"的典型。这类问题单元测试很容易漏，因为没人会去试
"一开一关"的组合。

## F-17 ⚠️ **项目无法编译为 Web** —— PCG32 用了 JS 无法表示的 64 位整数

**这是本阶段最重要的发现，直接关系到目标里「为 Web 阶段预留扩展性、
避免二次重写」这一条。**

**事实**：项目**从未配置 web 平台**（无 `web/` 目录），因此
「能否编译为 Web」**从来没有被验证过**。本轮补上验证后：

```
$ flutter build web --release
lib/game/core/random_source.dart:64:35:
Error: The integer literal 0xDA3E39CB94B95BDB can't be represented exactly in JavaScript.
lib/game/core/random_source.dart:73:30:
Error: The integer literal 0xFFFFFFFFFFFFFFFF can't be represented exactly in JavaScript.
lib/game/core/random_source.dart:74:34:
Error: The integer literal 6364136223846793005 can't be represented exactly in JavaScript.
```

**根因**：`Pcg32` 用 64 位状态与 64 位乘法（PCG 的标准实现）。
在 Web 上 Dart 的 `int` 是 double（仅 53 位安全），因此这些字面量
**编译期就被拒**。

**为什么这条特别严重**：
* PCG32 是**整个确定性架构的地基** —— 回放（`T-CORE-04`）、
  AC-01 的 100 seed 一致性、AC-06 的通关基准，全部依赖它；
* 也就是说，**Web 阶段一开始就会撞上它**；
* 静态检查（`grep dart:io` 等）**查不出这类问题** —— 只有真正编译
  才会暴露。

**修复方向**（研发可做，但工作量不小，且需要你确认优先级）：
* (A) 改用 `package:fixnum` 的 `Int64` 实现 PCG32 —— 跨平台一致；
* (B) 用两个 32 位半字手工实现 64 位乘法（不引依赖，代码更绕）；
* (C) 为 Web 换一个 32 位 PRNG —— **但这会破坏跨平台回放一致性**，
  不建议。

研发建议 **(A)**：`Int64` 在 VM 与 JS 上都精确，且回放摘要能保持一致。

**✅ 已修复（2026-10-14）**：
用 `package:fixnum` 的 `Int64` 重写了 `Pcg32`（详见 F-18）。
`flutter build web --release` 现在**通过**：

```

✓ Built build/web
```

（`--wasm` 的 dry run 也通过。）
`web/` 脚手架保留 —— 它是后续 Web 阶段的基础。

## F-18 ⚠️ **PRNG 并不是它声称的 `pcg32-xsh-rr`**（与 F-17 同根）

在准备修 F-17（Web 无法编译）时，我对现有 `Pcg32` 做了一次**权威对照**：
用 Python（任意精度整数）按 PCG32 标准实现同样的种子与构造函数，
比对前 5 个输出。

**结论：不一致。**

```
标准 pcg32-xsh-rr:  3964690459  723184244  1893306317   542306440  409935723
现有实现:             332423220  723446388  1893691445  1616048264  409935723
```

**根因**：PCG32 的 XSH-RR 输出函数要求**逻辑右移**：

    xorshifted = ((state >> 18) ^ state) >> 27     // 应为 uint64 逻辑右移
    rot        = (state >> 59) & 31                // 同上

而 Dart 在 VM 上 `int` 是**有符号 64 位**，对负数（状态高位为 1 时）
`>>` 是**算术右移**（符号扩展）。因此当 `state` 为负时输出偏离标准。

**这是一处实现偏离规范**：技术水平协议把 `prngAlgorithm` 固定为
`pcg32-xsh-rr`，代码也如此自报（`algorithm => 'pcg32-xsh-rr'`），
但实际不是那个算法。

**为什么必须让你定**：修好它（用 `Int64` 做无符号运算）会
**改变所有随机抽取** —— 影响种子相关的平衡，
并且已固化的东西都要重生成：

* `test/fixtures/replays/baseline_determinism_v1.json`（事件摘要会变）；
* AC-01 里"不同 seed 产生不同轨迹"的断言仍成立，但具体数值会变；
* 任何按当前序列调过的数值手感都基于一个**非标准**序列。

**✅ 已按 (A) 修复（2026-10-14）** —— 依据是技术水平协议第 103 行：
「选择可复现 PRNG（**例如 PCG32/Xoshiro 系列**），将**算法名**和 seed
写入 `RunStarted`；禁止依赖 Dart 默认 Random 的跨版本序列。」
规范并未强制必须是标准 PCG32，但**要求算法名如实**，而代码自报
`pcg32-xsh-rr` —— 因此"让实现符合自己的声称"属于**修缺陷**。
且 AC-06 表明**从未有人试玩过**，不存在需要保护的已调平衡。

修复后用 Python 权威参照逐值对照，前 5 个输出**完全一致**：
```
标准/新实现: 3964690459 723184244 1893306317 542306440 409935723
```
新增 `test/unit/core/pcg32_reference_test.dart` 固化这条对照。

**两条原始备选（保留备查）**：

* **(A) 修成标准 PCG32**（推荐）
  用 `package:fixnum` 的 `Int64` 实现无符号 64 位运算。
  一次同时解决 F-17（Web 可编译）与 F-18（名副其实）。
  代价：重生成回放夹具；种子相关的数值表现会变（但那是修正噪声，
  而不是破坏已调好的平衡 —— 因为此前的平衡本就建立在一个
  非标准序列上）。
* **(B) 只修 Web 兼容，保留现有序列**
  即"把现在的算术右移行为照样用 Int64 复刻一遍"。
  能让 Web 编译通过、且不改变任何现有数值，
  但**继续自报一个名不副实的算法**，且未来难以解释。

**研发建议 (A)**。但因为它改变随机行为，**不擅自动手**。

**另注**：这也解释了为什么此前没人发现 —— 确定性测试只验证
"同种子两次一致"，不验证"是否等于标准算法"。**这类"自报算法名
但实现不符"的问题，只有与权威参照对照才会暴露。**
