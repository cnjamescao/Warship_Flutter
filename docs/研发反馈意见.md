## 2026-10-15 发布构建实机试玩复核（**未通过发布验收**）

**复核范围与证据**：以当前工作区重新构建的 macOS Release
`build/macos/Build/Products/Release/warship_flutter.app` 进行实际操作：
首页 → 设置 → 开始战斗 → 简报 → 战斗 HUD → 首次升级草案。
同时已执行 `flutter analyze`、729 项非 Golden 测试、6 项 Golden 测试、
macOS Release 构建及 Web Release 构建；上述自动化与构建均通过。

**结论**：可以启动、进入战斗、触发升级草案，故“可以玩”这一最低判断成立；
但**不符合 v2.0 可交付/可发布标准**。原因不是规范或素材缺失，而是界面把
已存在的内容键和产品数据错误地直接展示给玩家，且现有测试未覆盖该真实界面。
在下列 F-25 全部关闭前，不得将当前版本标记为“符合 v2.0 要求”或进入发布验收。

### F-25-01（P0，阻塞发布）：升级草案向玩家暴露内部 ID 与未解析文案 Key

**实测现象**：首次草案中，卡片标题显示 `UP-PULSE-RATE`、
`UP-LASER-UNLOCK`、`UP-MISSILE-UNLOCK` 等内部 ID；描述显示
`up.pulseRate.desc`、`up.laserUnlock.desc`、`up.missileUnlock.desc` 等 Key。

**根因定位**：`DraftCardView` 已正确携带 `nameKey` 与 `descKey`，
`strings_zh_CN.json` 也已提供对应中文；但
`lib/app/v2_run_screen.dart` 的 `_DraftCard` 仍渲染 `card.cardId` 与
`card.descKey` 的原始字符串，未通过 `catalog.text(...)` 解析，且标题没有使用
`card.nameKey`。

**一线研发必须执行的动作**：

1. 卡片标题固定改为解析 `card.nameKey`；卡片描述固定改为解析 `card.descKey`。
   `card.cardId` 只可用于领域数据、日志、测试选择器，不得出现在面向玩家的 UI。
2. 无论缺失何种文案 Key，发布构建不得把 Key/ID 回退展示给玩家；采用既有内容加载
   失败策略记录诊断，并使该内容校验/测试失败。
3. 新增**运行时 widget/集成测试**：构造至少一张草案卡并断言可见中文标题、中文描述；
   同时断言页面文本不含 `UP-` 和 `up.` 这两类内部标识。不能只做静态扫描或
   `ContentCatalog` 单元测试。
4. QA 在 macOS Release 和 Web Release 各实际触发一次草案，留存截图；三张卡均不得
   出现 Key/ID。

**关闭准则**：以上自动化测试通过，并附两端真实草案截图；截图中所有卡片标题与描述
均为可读的中文玩家文案。

### F-25-02（P1，阻塞产品验收）：作战简报把“3 秒展示倒计时”误写成游戏目标

**实测现象**：简报页显示“坚持 3 秒，击败守门者 Aegis”。

**根因定位**：`briefing.objective` 当前把 `{seconds}` 解释成战斗目标，而
`V2AppFlow` 传入的是简报展示倒计时常量 `kBriefingCountdown = 3`。
产品基线明确的是：Boss 于有效战斗 150 秒入场、180 秒未击败进入狂暴、190 秒超时失败；
3 秒只属于简报表现时间，不能作为生存目标。

**一线研发必须执行的动作**：

1. 将“作战目标”与“3/2/1 倒计时”拆成两个独立展示语义；倒计时只能使用
   `briefing.countdown`，不得作为 `briefing.objective` 参数。
2. 目标文案按产品基线展示为：**“150 秒后守门者 Aegis 入场；190 秒内击败它”**。
   该句是本条的最终产品裁决；若以内容配置实现，应使用不含倒计时参数的独立 Key。
3. 新增 widget/集成测试：简报页面必须包含上述目标，且不得出现“坚持 3 秒”。
   另分别覆盖倒计时从 3 到 1 的显示，证明两个语义不再共用参数。

**关闭准则**：macOS Release 与 Web Release 简报截图均显示正确目标，倒计时单独显示，
并通过上述自动化断言。

### F-25-03（P2，不阻塞修复验证但必须纳入无障碍回归）：暂停按钮的辅助标签描述了错误状态

**实测现象**：战斗正在进行、按钮图标为“暂停”时，辅助功能树把该按钮标成“已暂停”。

**根因定位**：按钮的 `Semantics.label` 复用了暂停覆盖层标题 `pause.title`，而没有描述
该按钮执行的动作。

**一线研发必须执行的动作**：运行中暂停按钮的可访问名称为“暂停”；暂停覆盖层中的继续
按钮为“继续”。不要把静态状态标题复用为可点击动作的标签。新增语义测试，验证运行态
可找到“暂停”按钮、暂停后可找到“继续”按钮。

**关闭准则**：语义测试通过，并在 macOS VoiceOver 或等效检查中确认两个状态的可访问名称
与可执行动作一致。

### 对测试与验收流程的强制补充

本次缺陷说明“全绿”不能等价于“合规”：现有测试证明规则与构建可运行，**不证明玩家
看到的是正确内容**。后续每一个覆盖层（简报、升级草案、风险门、结算）都必须至少有一条
运行时可见文本断言；涉及配置的字段须验证“配置 Key → 解析文字 → 实际 Widget”的完整链路。
修复 F-25 后，研发须重新提交 macOS Release/Web Release 的截图证据和新增测试结果，
再申请本负责人进行第二次发布验收。

### F-26-01（P0，阻塞发布）：从正常开局流程进入战斗后，键盘焦点没有可靠交给游戏

**玩家实测与复现**：从首页点击“开始战斗”、跳过简报后，持续按 `A` / 左方向键，
战舰不向左移动，始终停在右下方。macOS Release 复测亦未观察到移动。

**这不是产品设计**：产品基线规定 WASD/方向键控制战舰移动；玩家**不应**在每局开始后
再点击画布、Tab 切换或进行任何额外动作才可控制。

**根因定位**：输入网关和移动规则本身实现了 A/D/方向键映射，但对局页只依赖
`Focus(autofocus: true)`。测试辅助 `focusGameField` 已明确记录：在
Home → Loading → Briefing → Playing 的正常重建链路后，该 Focus 节点没有拿到焦点，
因此测试只能额外手动 `requestFocus()` 才能让键盘事件到达游戏。这正是本次实机故障，
不是可接受的测试前置条件。

**一线研发必须执行的动作**：

1. 在 `V2RunScreen` 实际挂载且进入可玩阶段后，可靠地将焦点交给 `warship-v2` 的
   游戏 Focus 节点；处理生命周期/覆盖层返回时也不得丢失可恢复的键盘控制。
2. 不能以“玩家先点画布”作为修复，也不能在验收测试中调用测试专用的
   `focusGameField`/直接 `requestFocus` 来绕过生产路径。
3. 增加从首页点击开始、经历完整简报、**不额外注入焦点**的 widget/integration 测试：
   发送按下并保持 `A`、`D`、左/右方向键后，读取运行时玩家 X 坐标，必须按相应方向变化；
   松键后必须停止。测试应覆盖 macOS 键盘事件路径。
4. QA 在 macOS Release 与 Web Release 各录制一段：开局后不点击战场，先向左移动、
   再向右移动，战舰必须清晰横移且不越界。

**关闭准则**：上述端到端测试不借助测试专用聚焦函数即可通过；两端录屏证明开局键盘
立即生效。

### F-26-02（P0，阻塞发布）：正式玩家战舰素材未在战场实际呈现

**玩家实测与复现**：战场右下角只见两个青色圆点，无法识别为玩家战舰；屏幕也出现敌机
的简化紫色三角形。玩家无法辨认自身位置与受击主体，这直接破坏躲避玩法。

**素材事实**：不是素材缺失。正式素材 `GFX-PLAYER-BASE` 已交付、登记为 firstRun、
运行时 PNG 为 512×512 的完整蓝白战舰。当前画面与该素材明显不符。

**根因定位范围**：渲染器在资源未取到时会静默回退到程序化图形；当前实机结果证明
`VisualAssetCache`/预载/路径解析/渲染缩放链路至少有一处没有让正式图片成功显示。
在未导出实际失败记录前，不把原因臆定为某一个路径错误。

**一线研发必须执行的动作**：

1. 在 macOS Release 与 Web Release 中检查 firstRun 预载结果和每个 `AssetLoadFailure`；
   修复使 `GFX-PLAYER-BASE`、首屏敌机和首屏投射物可实际从 manifest 路径加载。
2. 发布构建不得把已声明为 `release_ready` 且属于首屏关键实体的资源静默降级为占位图。
   对 `GFX-PLAYER-BASE` 建立启动前/首帧资源就绪断言；失败必须阻断进入可玩状态并给出
   可诊断错误，而非让玩家面对“两个圆点”。
3. 新增带真实预载的集成/端侧验证：首帧读取缓存，断言玩家图片可取；同时对战场截图
   做人工视觉验收，确认玩家是可辨认的战舰而非圆点/简化几何图形。
4. 修复后提供 16:9 和当前 macOS 窗口比例两张战斗截图；玩家机体必须始终可见、与敌机
   及我方投射物有明显视觉区分。

**关闭准则**：两端的 Release 截图均可清楚辨认正式玩家战舰，且首屏关键资产无加载失败。

### F-26-03（P1，阻塞产品视觉验收）：升级卡图标素材已交付，但草案 UI 从未使用它

**玩家实测**：升级卡除稀有度边框/叠层外没有“脉冲、导弹、激光”等能力图标，选择增强
缺少快速识别和视觉反馈。

**素材事实**：不是游戏没有提供素材。16 张逐卡图标已经以 `UI-UP-*` 交付；每张升级配置
也已经在 `iconAssetId` 中精确绑定，例如 `UP-PULSE-RATE` → `UI-UP-PULSE-RATE`。

**根因定位**：`DraftCardView` 携带 `iconAssetId`，但 `_DraftCard` 仅绘制稀有度素材；
没有任何路径把 `card.iconAssetId` 解析并渲染为卡片图标。因此是**研发未接入既有素材**，
不是素材或规范缺口。

**一线研发必须执行的动作**：

1. 每张草案卡必须通过 manifest/runtimeFiles 解析并显示它自己的 `card.iconAssetId`；
   禁止写死文件路径或用系列通用图标替代逐卡图标。
2. 图标放置于卡片标题上方/左侧的固定图标位，不能被稀有度叠层、文字或点击层遮挡；
   正常、焦点、按下、禁用状态按素材规范选取相应状态。
3. 增加测试：给定三张不同 `iconAssetId` 的草案，断言 UI 请求的运行时文件彼此对应；
   再以截图/视觉测试确认三张卡显示三种不同能力图标。
4. QA 用首次草案和包含导弹/激光的草案各验一次，截图中必须能在不读长描述的情况下
   识别卡牌类型。

**关闭准则**：所有草案卡均显示其配置指定的独立图标，截图与素材清单逐项可追溯。

### F-27（P0，阻塞素材与发布验收）：基础敌机及跨语义图形存在占位/重复副本

**审计范围**：对 `assets/images/v2` 的运行时 PNG、`素材/图形` 的源 SVG/运行时母版，
以及 `assets/config/v2/manifest.json` 的状态映射做了逐文件存在性、SHA-256 和人工图像核验。

**结论**：敌机文件名、manifest 记录和运行时路径都存在，因此不是“缺文件”；但**内容不合格**。
`Scout`、`Wing`、`Sniper`、`Bomber` 四种基础敌机并没有各自的造型：

| 应独立的敌机 | 实测结果 |
| --- | --- |
| `GFX-EN-SCOUT` | 与 Wing/Sniper/Bomber 共用相同源 SVG；idle/hit/critical/destroy 分别与其他三类逐字节相同 |
| `GFX-EN-WING` | 同上 |
| `GFX-EN-SNIPER` | 同上（仅 `charge` 文件单独存在） |
| `GFX-EN-BOMBER` | 同上（仅 `drop` 文件名额外存在，内容仍与通用 hit 图相同） |
| `GFX-EN-SHIELD` | 有独立文件集，但 body 是通用盾形/十字图，与精英光环和 UI 焦点环复用，不可作为独立护盾机机体交付 |

具体证据：四个基础敌机的源 SVG SHA-256 完全相同；23 个敌机 PNG 仅有 10 个不同的
文件哈希，其中 Scout/Wing/Sniper/Bomber 的 idle、hit、critical、destroy 各自形成四份
完全相同的副本。实际查看 idle 图是一张通用盾形十字图，不能表达侦察机、翼虎机、狙击机、
轰炸机的玩法身份。该图还与 `GFX-FALLBACK-SILHOUETTE` 等无关资源完全相同，进一步证明
它是占位/回退图而非敌机成品。

**范围外但已确认的正向事实**：`GFX-BOSS-AEGIS-BODY` 的 p1/p2/p3 是三张不同图片，
玩家战舰基础 PNG 也是完整的战舰图；因此不能以“所有素材都未生成”概括。但运行时素材包
整体也存在严重的跨语义重复：368 张 PNG 只有 108 个不同哈希。禁用态/透明态的合理共用
可保留，然而普通态中“敌机、投射物、HUD、升级图标、回退图”跨类别共用同一张图不可接受。

**一线研发与素材制作必须执行的动作**：

1. 由美术/素材负责人重做并交付五种基础敌机的**独立**机体：Scout、Wing、Sniper、
   Bomber、Shield。每一种至少提供产品清单要求的 idle、hit、critical、destroy 状态；
   Sniper 另有 charge，Bomber 另有 drop。状态图必须表达自身机体的受击/濒危/摧毁，
   不能用通用符号、UI 元素或回退剪影替代。
2. 同步更新源设计文件、源 SVG、运行时 PNG、manifest 的哈希和版本；不得只替换
   `assets/images/v2` 中的一个副本，否则素材源与发布包会再次分叉。
3. 逐项清理“跨语义复用”的普通态占位图，优先处理敌机、玩家/敌方投射物、武器效果、
   升级图标、HUD 关键图标与风险门图形。合理的纯透明 disabled 占位可列入白名单，
   其余重复必须逐项说明设计意图并经素材负责人批准。
4. 新增素材 CI 审计：对角色/敌机/武器/升级图标等“语义上必须可区分”的 Asset ID，
   运行时首图的 SHA-256 不得重复；允许重复的状态必须在版本化白名单中标明原因。
5. 在接入代码前交付一张带 Asset ID 的敌机/状态联系表和人工验收拼图；研发仅按 manifest
   接入，不得自行用占位图代替未完成素材。

#### v2.0.7 追加核验（2026-10-16）

玩家实机提到的 `GFX-PLAYER-SHIELD-HIT` 已确认是通用状态图而非独立护盾命中效果，

## F-03 结算奖牌算法：产品基线 §8 vs 技术协议 §3.1（已裁决、已追认）

**冲突原文**：
* 产品基线 §8：「胜利为 Gold；Boss HP ≥35% 的失败为 Silver；其余为 Bronze。」
* 技术协议 §3.1：「gold；失败但曾进入 Boss P3（`bossHpRatio < 0.35`）
  silver；失败且存活 ≥120 秒 bronze；其余 `none`。」

**裁决**：按交付清单 §8「产品基线 → 技术协议 → …」，
**产品基线优先**。实现为：

| 情形 | 结果 |
| --- | --- |
| 胜利 | `gold` |
| 失败且把 Boss 打进 P3（`< 0.35`） | `silver` |
| 其余失败 | `bronze` |
| — | **不产生 `none`** |

**产品负责人追认（2026-10-16）**：以上实现为正式 v2.0 定义。产品基线 §8 已改为
“失败且 Boss 剩余 HP <35% 为 Silver；其余失败为 Bronze；不产生 none”，消除阈值方向
歧义。研发无需更改已按该规则完成的代码或素材，只需在后续回归中按此单一口径断言。

**原裁决理由（保留审计记录）**：
1. **阈值方向**。产品基线只写「Boss HP ≥35%」没说方向。按字面读
   「剩余 HP ≥35% 才 Silver」会**打得越差奖牌越好**，与它自己的
   档位排序（Silver > Bronze）矛盾。故以技术协议的显式算法解释它。
2. **`none` 的存废**。技术协议给 `none`、产品基线说「其余为 Bronze」，
   直接冲突 → 按 §8 判产品基线优先，故不产生 `none`。

技术协议已于 2026-10-16 同步为上述规则；不再保留“是否启用 none”的待确认项。

## F-05 条件绑定无法被任何适配器产出（16 项）

`lib/game/infrastructure/audio_director.dart` 的 `conditionalParamsOf`
是 Domain 事件 → 条件参数的**唯一适配器**，它只覆盖 36 个事件里的 19 个。
凡没有分支的事件，参数 map 为空，**其带条件的绑定永远匹配不上**。
共 16 项，分三类：

1. **适配器完全没有该事件的分支**（7 项）：
   `UiCommand` 的 `command`、`EnemyDefenseStateChanged`、
   `EnemyVitalStateChanged`、`RiskOptionStateChanged`、
   `WeaponSustainStarted/Stopped` 的 `weaponId`。
   → 后两个直接关系**激光循环音的起停**（防叠音）。
2. **有分支但键名不一致**（3 项）：
   * `PlayerDamaged` 适配器产 `hpDamage`/`shieldDamage`，
     绑定却要 `hpRatio`/`shieldRatio`
   * `RiskGateOpened` 适配器产 `gateId`，绑定要 `optionId`
3. **适配器不产出的状态类键**（6 项）：
   `availability`、`frontShieldActive`、`state`、`controlId`、`resultTier`。

**已做的**：这 16 项已冻结为已知集合并加断言（
`test/game/acceptance_visual_states_test.dart`），防止继续扩大。
**待定**：需要确认每一项是"该事件本该有分支而漏了"还是"绑定写错了
事件名/条件键"。**这属于内容与协议的交叉问题，研发不擅自改动素材绑定。**

## F-17 ⚠️ **项目无法编译为 Web** —— PCG32 用了 JS 无法表示的 64 位整数

**这是本阶段最重要的发现，直接关系到目标里「为 Web 阶段预留扩展性、
避免二次重写」这一条。**

**事实**：项目**从未配置 web 平台**（无 `web/` 目录），因此
「能否编译为 Web」**从来没有被验证过**。本轮补上验证后：

```
$ flutter build web --release

Error: The integer literal 0xDA3E39CB94B95BDB can't be represented exactly in JavaScript.
lib/game/core/random_source.dart:73:30:
Error: The integer literal 0xFFFFFFFFFFFFFFFF can't be represented exactly in JavaScript.
lib/game/core/random_source.dart:74:34:
Error: The integer literal 6364136223846793005 can't be represented exactly in JavaScript.
```

**根因**：`Pcg32` 用 64 位状态与 64 位乘法（PCG 的标准实现）。
在 Web 上 Dart 的 `int` 是 double（仅 53 位安全），因此这些字面量
**编译期就被拒**。

**为什么这条特别严重**：
* PCG32 是**整个确定性架构的地基** —— 回放（`T-CORE-04`）、
  AC-01 的 100 seed 一致性、AC-06 的通关基准，全部依赖它；
* 也就是说，**Web 阶段一开始就会撞上它**；
* 静态检查（`grep dart:io` 等）**查不出这类问题** —— 只有真正编译
  才会暴露。

**修复方向**（研发可做，但工作量不小，且需要你确认优先级）：
* (A) 改用 `package:fixnum` 的 `Int64` 实现 PCG32 —— 跨平台一致；
* (B) 用两个 32 位半字手工实现 64 位乘法（不引依赖，代码更绕）；
* (C) 为 Web 换一个 32 位 PRNG —— **但这会破坏跨平台回放一致性**，
  不建议。

研发建议 **(A)**：`Int64` 在 VM 与 JS 上都精确，且回放摘要能保持一致。

**✅ 已修复（2026-10-14）**：
用 `package:fixnum` 的 `Int64` 重写了 `Pcg32`（详见 F-18）。
`flutter build web --release` 现在**通过**：

## F-18 ⚠️ **PRNG 并不是它声称的 `pcg32-xsh-rr`**（与 F-17 同根）

在准备修 F-17（Web 无法编译）时，我对现有 `Pcg32` 做了一次**权威对照**：
用 Python（任意精度整数）按 PCG32 标准实现同样的种子与构造函数，
比对前 5 个输出。

**结论：不一致。**

```
标准 pcg32-xsh-rr:  3964690459  723184244  1893306317   542306440  409935723
现有实现:             332423220  723446388  1893691445  1616048264  409935723
```

**根因**：PCG32 的 XSH-RR 输出函数要求**逻辑右移**：

    xorshifted = ((state >> 18) ^ state) >> 27     // 应为 uint64 逻辑右移
    rot        = (state >> 59) & 31                // 同上

而 Dart 在 VM 上 `int` 是**有符号 64 位**，对负数（状态高位为 1 时）
`>>` 是**算术右移**（符号扩展）。因此当 `state` 为负时输出偏离标准。

**这是一处实现偏离规范**：技术水平协议把 `prngAlgorithm` 固定为
`pcg32-xsh-rr`，代码也如此自报（`algorithm => 'pcg32-xsh-rr'`），
但实际不是那个算法。

**为什么必须让你定**：修好它（用 `Int64` 做无符号运算）会
**改变所有随机抽取** —— 影响种子相关的平衡，
并且已固化的东西都要重生成：

* `test/fixtures/replays/baseline_determinism_v1.json`（事件摘要会变）；
* AC-01 里"不同 seed 产生不同轨迹"的断言仍成立，但具体数值会变；
* 任何按当前序列调过的数值手感都基于一个**非标准**序列。

**✅ 已按 (A) 修复（2026-10-14）** —— 依据是技术水平协议第 103 行：
「选择可复现 PRNG（**例如 PCG32/Xoshiro 系列**），将**算法名**和 seed
写入 `RunStarted`；禁止依赖 Dart 默认 Random 的跨版本序列。」
规范并未强制必须是标准 PCG32，但**要求算法名如实**，而代码自报
`pcg32-xsh-rr` —— 因此"让实现符合自己的声称"属于**修缺陷**。
且 AC-06 表明**从未有人试玩过**，不存在需要保护的已调平衡。

修复后用 Python 权威参照逐值对照，前 5 个输出**完全一致**：
```
标准/新实现: 3964690459 723184244 1893306317 542306440 409935723
```
新增 `test/unit/core/pcg32_reference_test.dart` 固化这条对照。

**两条原始备选（保留备查）**：

* **(A) 修成标准 PCG32**（推荐）
  用 `package:fixnum` 的 `Int64` 实现无符号 64 位运算。
  一次同时解决 F-17（Web 可编译）与 F-18（名副其实）。
  代价：重生成回放夹具；种子相关的数值表现会变（但那是修正噪声，
  而不是破坏已调好的平衡 —— 因为此前的平衡本就建立在一个
  非标准序列上）。
* **(B) 只修 Web 兼容，保留现有序列**
  即"把现在的算术右移行为照样用 Int64 复刻一遍"。
  能让 Web 编译通过、且不改变任何现有数值，
  但**继续自报一个名不副实的算法**，且未来难以解释。

**研发建议 (A)**。但因为它改变随机行为，**不擅自动手**。

**另注**：这也解释了为什么此前没人发现 —— 确定性测试只验证
"同种子两次一致"，不验证"是否等于标准算法"。**这类"自报算法名
但实现不符"的问题，只有与权威参照对照才会暴露。**

## F-23 更新 golden 基线（`draft.png`）—— 因 PCG32 修复引起的正当变化

**事件**：修好 PCG32（F-17/F-18）后，**golden 测试出现 1 个失败**：
`draft.png`（升级草案）差异 **1.04% / 44857 像素**。

**这是我此前漏掉的验证**：我改了 PRNG 却**只重跑了非 golden 测试**
（`--exclude-tags golden`），没有重跑 golden。**是我自己造成的疏漏**，
在本轮"完整三端验证"时才发现。

**差异性质分析**（用 Pillow 量化，而不是直接更新了事）：
* 差异是**单一连续区域** `y=727..1202, x=1012..1789`，宽约为画面 1/3
  —— **正好是「一张卡」的位置**；
* 与机制吻合：升级草案的**保底卡固定**（`guaranteedFirstDraft`），
  只有随机那张会变。PCG32 修复后**保底卡不变、随机卡变了**。

**处置**：重生成 `draft.png`。重生成后：
* golden **6/6 通过**；
* `git status` 显示**只有 `draft.png` 一个基线文件变化**；
* 新旧基线差异 **44857 像素（1.04%）** ——
  与失败时的差异**完全一致**，说明重生成**只捕获了这一处变化，
  没有夹带其它改动**。

**为什么要把这件事写下来**：更新 golden 基线**是最容易掩盖真实回归的
操作**（"测试红了就更新基线"）。因此这里记录了：差异的量化、位置的
解释、变化文件的唯一性、以及差异大小与失败时一致 ——
**让这次更新可被复核，而不是一句"基线已更新"**。

**教训**：改了随机源、内容版本或素材后，**必须把 golden 一起重跑** ——
