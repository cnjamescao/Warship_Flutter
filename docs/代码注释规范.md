# Warship v2.0 代码注释规范

> **确立日期**：2026-10-16
> **依据**：产品负责人确立的默认工作要求 ——「所有代码要有非常详细完整的注释说明；
> 目标是**以后的工程师可以通过注释说明，明白代码思路和架构**」。
> **适用范围**：`lib/` 下的全部 Dart 源码（`tool/`、`test/` 一并遵循，test 可适度从简）。

---

## 一、衡量标准（不是"有注释"，而是"能接手"）

一份合格的注释应当让**从未参与本项目的工程师**在不读实现细节的前提下回答：

1. **这个文件在整个架构里处于哪一层？**（Domain / Core / Presentation / App / Infrastructure）
2. **它为什么存在？**（解决什么问题，不解决什么问题）
3. **它与其他模块的契约是什么？**（谁调用它、它调用谁、数据如何流动）
4. **有哪些**非显然的约束**？（不变量、时序要求、平台限制、易错点）
5. **为什么这样实现，而不是另一种显然的做法？**（权衡与取舍）

**反例**：`// 返回玩家血量`（复述代码，无信息量）。
**正例**：见第二节模板。

## 二、必须包含的四类注释

### 2.1 文件头（每个 `.dart` 必备）

```dart
// ================================================================
// lib/game/presentation/warship_v2_game.dart —— 表现层主组件
// ================================================================
// **架构位置**：Presentation。Flame 组件，把 Core 产出的 RenderSnapshot
//   画成画面；**不持有任何规则状态**。
//
// **为什么存在**：Core 只产出不可变快照，绘制与规则彻底分离 ——
//   使"表现不影响规则"成为可测试的性质（见 T-RULE-01）。
//
// **与谁交互**：
//   * 上游：`GameRuntime.snapshot()`（每帧一份不可变快照）
//   * 下游：Flame 的 `Canvas`；资源来自 `VisualAssetCache`
//
// **关键约束**：
//   * 预警必须画在**背景之上、实体之下**（协议 §3.2）
//   * 只用 manifest 绑定的正式素材，不得用 Canvas 几何替代
//   * 任何绕过 `_drawSpriteOrNull` 的绘制**必须**自行登记到
//     `drawnAssetMaxRadius`（否则视觉断言会误报）
//
// **易错点（血泪）**：线形预警用 `drawImageRect` 直接绘制，
//   曾三次漏记绘制记录；素材画布是 512×512 而内容只占 500×72，
//   按画布高度算带宽会把横带纵向拉伸 7 倍。
// ================================================================
```

### 2.2 公开类型（`class` / `enum` / 顶层函数）

必须说明：**职责**、**在架构中的角色**、**不变量**。
若该类型对应某条产品/技术合同的实现，**引用合同出处**（§号或 F-编号）。

### 2.3 公开成员（方法/字段）

说明**契约**而非实现：参数含义与合法域、返回语义（含 null 的含义）、
副作用、抛错条件、时序要求。

### 2.4 非显然实现处的行内注释

只在**读代码看不出来**的地方写：为什么用这个算法、为何跳过某分支、
边界为何这样取、以及**曾经的缺陷与教训**。

## 三、鼓励记录「为什么不是另一种做法」

本规范特别要求记录**被否决的方案**。例如：

> 曾按 `attackId` 去 manifest 查绑定，但 `sniper_line` 同时绑定
> 机体（448×448）与预警（512×512）两张图，按 attackId 会命中机体 ——
> 于是把战机贴图当预警线拉伸旋转。故改用 Domain 在 t=0 锁定的
> `telegraphAssetId`（F-38）。

这类注释能**阻止后人在同一个坑里再掉一次**，价值高于描述性注释。

## 四、自动化守卫

`test/architecture/comment_standard_test.dart` 强制以下**机械可查**的项：

| 检查 | 规则 |
| --- | --- |
| 文件头 | 每个 `lib/**/*.dart` 的前 20 行内必须有 `// ====` 分隔的文件头块 |
| 架构位置 | 文件头块内必须出现 `架构位置` 字样 |
| 公开类型 | 每个 `class` / `enum` 声明前必须紧跟 `///` 文档注释 |
| 公开方法 | 每个**公开**方法（不以 `_` 开头）前必须有 `///` 文档注释 |
| 禁止空注释 | `///` 后不得为空或仅含标点 |

**密度不作为硬指标** —— 注释质量无法用行数衡量；
但作为**进度参考**，`lib/` 平均注释密度应逐步提升
（截至 2026-10-16 基线：**29%**，59 个文件）。

## 五、落地批次（渐进执行，不做一次性大改）

| 批次 | 范围 | 理由 | 状态 |
| --- | --- | --- | --- |
| **B1** | 架构入口：`main.dart`、`v2_bootstrap.dart`、`game_runtime.dart` | 接手者最先读这三个 | ⬜ |
| **B2** | Domain 五系统：`player/enemy/boss/director/weapon_system` | 规则核心，改动风险最高 | ⬜ |
| **B3** | 内容与素材：`content_catalog`、`asset_manifest`、`asset_cache` | 资源链路的理解成本最高 | ⬜ |
| **B4** | 表现层：`warship_v2_game`、`v2_run_screen`、`visual_router` | 视觉验收相关，坑最多 | 🔶 部分（本轮改动处已有详细注释） |
| **B5** | 其余文件 | 补齐即可 | ⬜ |

**每批完成后**：跑 `flutter analyze` + 全量测试 + 注释守卫，确认无回归。
