## 五、未完成工作

### 5.1 研发可直接完成项已全部关闭（F-42 / F-43）

**F-42 已按方案 A 修复并验收通过。**`test/fixtures/performance/*.json` 是受版本控制的**只读基线输入**，正常 `flutter test` 不得修改它；本次测量报告写入 `build/` 或系统临时目录，且该报告不纳入提交。只有显式 `UPDATE_PERF_BASELINE=1` 的维护流程允许重建基线；该路径不得成为普通 CI/本地回归的副作用。

由于毫秒成本依赖机器，历史 p50/p95/p99 **不得**直接作为跨机器硬阈值。F-43 已补齐：读取基线后校验 schema、`seed`、`contentVersion`、场景时长和对象预算，并输出“基线值 / 本次值 / 差值 / 比例”的完整信息性比较；同时保留本次采样完整报告、对象上限、降级与逻辑正确性守卫。真正的帧时间、内存与发布性能门禁仍由 AC-07 的真机 Release 采样决定。

## 七、本轮建立的**诊断与守卫**（长期资产）

这些是把「**静态检查通过 ≠ 画面正确**」这个反复踩坑处交给机器把守的机制：

| 机制 | 作用 |
| --- | --- |
| `drawnAssetMaxRadius` + 累积绘制历史 | 运行时上报"这一帧实际画了哪些资源、画了多大"，落盘到沙盒可写目录 |
| 预警几何上报 | 输出 `len` / `band` / `rot` / 素材尺寸，用于定性"画出来是什么" |
| **绘制记录覆盖度守卫** | 断言每处 `drawImageRect` 都进记录，防止盲区复发（我为此踩过三次） |
| 实体外观 vs 事件视觉守卫 | 防止"事件资源顶替实体外观"（F-28 / F-31 同类） |
| 重复素材守卫 | 按**文件内容**比对，冻结重复规模 |
| 素材溯源守卫 | 源稿 → 运行时 → 应用侧逐环哈希校验 |

## 【重要】Golden 超时的**真实根因**（2026-10-21 确认）

### 结论

> **`loadV2CatalogForTests()` 不能在 `testWidgets` 的回调里 `await`。**

在 `testWidgets` 里 `await` 它会**永远挂住**（测试跑满 10 分钟超时），
因为该回调运行在 **fake-async 区**，真实 IO 的 Future 不会完成。

### 正确写法

```dart
late ContentCatalog catalog;

void main() {
  TestWidgetsFlutterBinding.ensureInitialized();
  setUpAll(() async {
    catalog = await loadV2CatalogForTests();   // ← 必须在 setUpAll
  });

  testWidgets('...', (tester) async {
    // 这里**只用**已加载好的 catalog，不再 await 任何真实 IO
    await mountV2App(tester, catalog);
  });
}
```

### 为什么值得单独记一条

我在 v2.1 期间**三次**在 Golden 上耗掉整轮（每次 10 分钟超时），
当时的误判是"`setUpAll` 里的目录加载挂住" ✗ —— **方向完全错了**，
真正的原因是"**在 `testWidgets` 内 await**" ✓。

后来在 `web_loading_timeout_test.dart` 上**再犯一次**，
把加载移到 `setUpAll` 后**立刻通过** ⇒ 根因被**双向证实** ✓。

**因此**：那四张结果徽记 Golden 的失败**不是**"Golden 不可行" ✗，
而是**写法错了** ✗ —— 下一次做时按上面的模板写即可。
（本结论修正了之前"三次尝试均失败，改用结构断言"的记录：
结构断言仍然有价值，但**不能**用它来证明"Golden 做不到"。）
