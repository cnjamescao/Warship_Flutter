## 逐项说明

### AC-01 100 个固定 seed 回放 — 🔶
「同输入下升级候选、风险门、精英词缀、得分和胜负完全一致」

- **已做**：100 个 seed 各跑 1200 帧（20 秒有效战斗，覆盖 15.0 秒的首个升级草案）。其中 12 个 seed **双跑比对**，断言事件摘要、得分、升级候选顺序、风险门可选项完全一致。
- **未做**：另外 88 个 seed 只跑一次（双跑全部 100 个会让测试时间翻倍）。精英词缀在 65 秒后出现，超出 20 秒窗口，**未被本用例覆盖**——需由更长的固定回放（AC-06 基准）补充。
- **注意**：事件摘要**刻意不含负载**（浮点坐标跨平台可能有极小差异），因此它验证事件**结构**确定性；数值一致性由 score 与候选列表比对保证。

### AC-02 横向分辨率 — 🔶
「16:9、4:3、21:9 和带安全区设备均不拉伸逻辑世界，HUD 不越界」

- **已做**：`CameraComponent.withFixedResolution(1920×1080)` 保证逻辑世界不与屏幕分辨率耦合；`ViewportMath` 提供屏幕↔逻辑换算并使 **letterbox 不吞输入**；widget 测试覆盖常规 resize、极小窗口（1×1）、极端长宽比。
- **未做**：**三种目标宽高比的真实截屏比对**（16:9 / 4:3 / 21:9）与 Golden 基线。

### AC-03 5 分钟生命周期循环 — ✅
「开始、暂停、失焦、升级、风险门、死亡、重开 20 次后无残留实体、持续音或重复输入」

- **已做**：`test/game/acceptance_lifecycle_test.dart` 跑满 20 轮。每轮都先断言新局是干净的（出生点、计数归零、无实体、无未消费事件），再走完「推进 3 秒 → 暂停 → 恢复 → 失焦 → 再推进制造投射物与危险区 → 死亡」全部路径，释放后逐项检查残留：敌人 / 投射物 / 危险区 / 未消费事件 / 待选草案 / 风险门 / Boss / 持续音句柄。
- **另断言**：循环结束后新开一局，实体序号从 1 重新开始（分配器未跨局累积）；重开不继承上一局的移动输入（防"粘键"）。
- **说明**：本用例覆盖的是**逻辑与音频句柄**层面的残留。Flutter Widget / Flame 组件的监听器残留由 `test/widget_test.dart` 与 `test/widget/hud_test.dart` 的既有回归覆盖。

### AC-04 公平性 — 🔶
「每种攻击在命中前有对应预警；生成点满足 360 px 安全距离；无不可躲避 Boss 循环」

- **已做**：
  * `test/game/acceptance_fairness_test.dart` 用 **boss_aegis.json 的真实参数**
    驱动公平性分析：造成伤害的招式必须预警 >0 且 ≥0.6 秒；扇形 24° 半角留有
    大片安全区；环形 70° 缺口构成非空安全区；激光预警内可离开路径；
    冲锋 0.8 秒内可横移离开（340×0.8=272 px > 所需 180 px）
  * 生成点安全：§6 的 ≥360 px（含"所有点都太近时延后"）与产品设计文档 §3.3
    的 ≥180 px 都有断言
  * **反向验证**：`缺口过窄时会被判定为不可躲避` 一条证明分析器确实会报出
    问题，而不是只会说"没问题"
- **未做**：**完整的"无不可躲避循环"可解性分析**。当前 `FairnessAnalyzer`
  把危险区视为**立即致命**，因此对"环形弹幕"这类**向外扩张**的招式会偏保守
  （玩家靠近 Boss 时实际拥有比预警时长更多的可用时间）。要给出可靠结论
  需要把**弹幕飞行时间**纳入模型，并做"招式序列 × 玩家可行走位"的联合搜索。

### AC-05 状态视觉（13 个） — 🔶
「产品设计文档 7.5 的全部 13 个状态均有正确视觉、音频和结束条件」

- **已做**：`AssetBindingTable` 覆盖真实 manifest 的**全部 368 条图形绑定与音频绑定**，逐条验证「事件 + when → Asset ID + renderState」精确解析；多状态资源的每个声明状态都有可达路径；`transientMs` 与 `restoreFromSnapshot` 语义被校验。
- **未做**：这份证据证明的是**路由正确**，而不是**画面正确**。缺少 13 个状态的截图/Golden 逐项比对。
- **13 个状态已逐项核验**：`test/game/acceptance_visual_states_test.dart`
  （30 个用例）按产品文档 §7.5 的表格逐行枚举 13 个状态，
  为每个状态构造对应事件与条件，断言视觉与音频两侧都能解析出资源，
  并断言命中的是**对的那个** Asset ID / cueId。
- **更正上一轮的误判**：上一轮我说这里"有 4 处真实路由缺口"，**那是错的**。
  本轮查明那 4 处**全部是我用错了事件**：
  * `GFX-BOSS-DEFEAT` 实际绑定在 `BossPhaseChanged`（我错用 `BossDefeated`）
  * `SFX-PLAYER-LOW-SHIELD` / `SFX-PLAYER-LOW-HP` 实际绑定在
    **`PlayerDamaged`** + `shieldDamageGt`/`hpRatioLte`（我错用
    `PlayerVitalStateChanged`，且条件键也写错了）
  * `SFX-BOSS-DEFEAT` 本来就绑定在 `BossDefeated`，音频一直是对的
- **新增一致性扫描**（本轮最有价值的产出）：遍历 manifest 的**每一个**
  绑定，取出 `when` 键，与"事件类型 → 实际携带字段"的声明表比对，
  一次性列出全部不匹配。首次运行报出 **26 处**，逐类收敛后归零。
  扫描同时守住"字段表必须覆盖全部 36 个事件与全部 21 个 `when` 键"。
  这与此前修过的 `weaponId: pulse` vs `WPN-PULSE` 是**同一类问题**，
  现在有了系统性的拦截手段。
- **死路由扫描（本轮新增，最关键的发现）**：`audioParamsOf` 是
  Domain 事件 → 条件参数的**唯一适配器**，因此它是契约的事实来源。
  扫描发现：**该适配器只覆盖 36 个事件里的 19 个**，
  而 manifest 有 24 个事件带条件 —— 凡适配器没有分支的事件，
  参数 map 为空，**其带条件的绑定永远匹配不上**。
  扫描冻结了 16 项「条件键无适配器产出」的绑定，分三类：
  1. **适配器完全没有该事件的分支**（7 项）：`UiCommand` 的 `command`、
     `EnemyDefenseStateChanged`、`EnemyVitalStateChanged`、
     `RiskOptionStateChanged`、`WeaponSustainStarted/Stopped` 的 `weaponId`
     —— 注意最后两个直接关系到激光循环音的起停（T-AUDIO-02 防叠音）。
  2. **有分支但产出的键名与绑定基名不一致**（3 项）：
     * `PlayerDamaged` 适配器产 `hpDamage`/`shieldDamage`，
       绑定却要 `hpRatio`/`shieldRatio`
     * `RiskGateOpened` 适配器产 `gateId`，绑定要 `optionId`
  3. **适配器根本不产出的状态类键**（6 项）：`availability`、
     `frontShieldActive`、`state`、`controlId`、`resultTier`
     —— 其中 `resultTier` 正是**文档冲突未裁决**的那一项。
- **本轮核实结果（重要架构发现）**：我查了 `resolveVisuals` 的全部调用点，
  结论是 —— **它在 `lib/` 里从未被调用**。生产代码里
  `AssetBindingTable` 的**唯一**消费者是 `AudioDirector` 的 `resolveCues`。
  表现层走的是另一条路：`BattlefieldComponent._drawSpriteOrNull()` 接收
  调用方传入的 `assetId`，来自运行时/域层（`RenderSnapshot`），
  再用 `VisualAssetCache.imageFor(assetId, state)` 取图。

  **因此 manifest 里的 368 条图形 `eventBindings` 在运行时没有被查阅。**
  它们是"声明了但没有运行时消费者"。

  这对验收的影响是实质性的：
  * **AC-05**：13 个状态的视觉当前**不是**由 manifest 绑定驱动的。
    我的用例是通过**手动调用** `resolveVisuals` 才断言成功的 ——
    这证明的是"绑定表本身正确"，**不等于**"游戏运行时会按它显示"。
    该项的评估因此应当下调。
  * 上一轮冻结清单里属于图形资源的条目，**确认是死路由**（无人调用）。
  * **AC-07 的降级**只作用于表现层自己绘制的层（星云网格、敌人血条、
    特效池），manifest 里的"视觉状态"不参与。

  **已确认为协议违反（本轮的最终结论）**：我上一轮写"不能断言这是缺陷、
  有两种可能、交用户裁决"—— 那个保留**是错的**。本轮回到文档查证，
  技术协议与素材规范都有明确规定：

  > 技术协议：「`AssetLoader` 必须在首次播放/渲染前将 `eventBindings`
  > 解析为不可变表，且只按 `event + when` 条件匹配，**禁止仅凭
  > `triggerEvents`、文件名或显示文本选资源**。」
  >
  > 素材规范 §1.1：「`eventBindings` 是**唯一允许消费的精确路由**……
  > `PresentationSystem` 根据本规范第 5.1 节和 `eventBindings` 将
  > DomainEvent 转为 `renderState`/`cueId`；**两者均不得猜测文件名或用
  > 显示文本查资源**。」

  当前实现让表现层直接使用来自 `RenderSnapshot` 的 `assetId`，
  **绕过了 `eventBindings`**，正是协议明文禁止的做法。因此：
  * 这是**实现缺陷**，不是设计选择；
  * **AC-05 不能算通过** —— 13 个状态的视觉没有被绑定表驱动；
  * 修复方向明确：表现层改为 `DomainEvent → resolveVisuals(event, params)
    → renderState`，与音频侧已经做对的方式（`resolveCues`）保持一致。
  * **本轮进度**：已实现 `lib/game/presentation/visual_router.dart`
    （`VisualRouter` + `RoutedVisual`），并抽出规范命名的
    `conditionalParamsOf`（视觉与音频共用同一套条件键空间）。
    **但它尚未接进 `BattlefieldComponent`，也没有测试覆盖** ——
    生产代码此刻仍然绕过绑定表。本轮我在给路由器写用例时把事件构造
    签名写错了，没有余量修正，因此按纪律移除了那个用例而不是提交坏测试。
  * **本轮已完成接线**：`WarshipV2Game` 建立 `VisualRouter`（由
    `visualAssets.manifest` 构建绑定表），每帧在绘制前
    `consume(runtime.lastFrameEvents)`；玩家与敌人两个绘制点
    优先使用路由结果（`route?.assetId ?? snapshot.assetId`），
    解析不出时才回退快照。**368 条图形 eventBindings 现在真正被消费。**
  * 新增 7 个路由器用例覆盖：敌人/玩家路由、无绑定事件不产生路由、
    瞬态过期回退、clear、后到覆盖先到、预警可解析。
  * 测试抓出我 router 里一个真实缺陷：`EnemySpawned`/`EnemyDestroyed`
    用了 `enemyId` 字符串做键，而 `EnemyDamaged` 用 `entityId` ——
    同一敌人有两个键，先写的路由永远查不到。已统一为 `entityId`。

### 已裁决的文档冲突：结算奖牌 `resultTier`（2026-10-14）

**冲突原文**：
* 产品基线 §8（第 239 行）：「结算评价：胜利为 Gold；Boss HP ≥35% 的失败为
  Silver；其余为 Bronze。」
* 技术协议 §3.1（第 93 行）：「胜利为 `gold`；失败但曾进入 Boss P3
  （`bossHpRatio < 0.35`）为 `silver`；失败、存活时间 ≥120 秒为 `bronze`；
  其余为 `none`。」

**裁决依据**：`Spec/开发者交付清单.md` §8 明文 ——
「若文档之间出现冲突，按以下优先级处理：**产品基线 → 技术协议 →
素材规范/manifest → 产品交互文档**」。因此**产品基线优先**。

**实现取舍**（全部集中在 `lib/game/domain/result_tier.dart`）：
| 情形 | 采用 | 理由 |
| --- | --- | --- |
| 胜利 | `gold` | 两份文档一致 |
| 失败且把 Boss 打进 P3 | `silver` | 产品基线只给片段、无方向；技术协议给显式算法。按字面读「剩余 HP ≥35% 才 Silver」会**打得越差奖牌越好**，与它自己的档位排序自相矛盾，故以技术协议解释产品基线 |
| 其余失败 | `bronze` | 产品基线「其余为 Bronze」明确兜底 |
| `none` | **不产生** | 技术协议给 `none`，产品基线给 `bronze`，直接冲突 → 按 §8 产品基线优先 |

**副产物：修掉一个真实缺陷。** 失败分支原先写死 `bossHpRatio: 0`，
而协议里 silver 的判定正是 `bossHpRatio < 0.35` —— 若照协议计算，
写死 0 会让**每一次失败都判成 silver**。现已改为传真实值
（Boss 未出现时记 1.0）。这也说明此前那个「硬编码 + 固定 'none'」
的组合掩盖了该缺陷。

**素材影响**：`UI-RESULT-MEDAL` 仍声明 4 个状态，`none` 现在
**声明但不可达**。资源校验不要求全部状态可达，故不受影响；
若后续要启用 `none`，只改 `resultTierFor` 一处。

**新增证据**：`test/unit/domain/result_tier_test.dart`（8 个用例，
含边界 0.35、null、以及「不产生 none」的显式断言）。

**落地（同日）**：

  `UI-RESULT-MEDAL` 对应 `renderState` 的运行时文件（**不硬编码
  文件名**，素材规范 §1.1），并显示本地化档位名
  （`result.tier.gold/silver/bronze`）。图形缺失时只显示文字，
  不影响结算可用性。
* `_onRunFinished` 用**真实** `boss?.hpRatio` 计算奖牌并传入结算页。

  （`{score}` / `{seconds}` 占位符替换）。

**首页文案本地化（同日）**：

  「所有展示文本使用本地化 key，不在玩法逻辑中硬编码」。
  现改为读 `app.title`（值为「Warship：霓虹最后防线」），
  按冒号拆成主/副标题两行 —— **版式不变，文案来源改为 key**；

* 现有 widget 用例仍断言 `WARSHIP` 与 `霓虹最后防线` 都在 ——

**仍未做**：设置页（背景音乐/音效/减少动效/触感反馈/返回）、

     仍须在 profile/release 构建的真机上采样。报告里已带 `scope` 字段标明。

1. **人工试玩**：确认玩法可通关 —— 这是 AC-06 与后续一切数值验收的前置。
2. **Golden 基线**：HUD / 升级草案 / 风险门 / 暂停 / 结算五个界面。
3. **真实设备与浏览器实测**：AC-07 与 AC-08 的逻辑层准备已完成，缺实测数据。
4. **Golden 基线的平台问题**：CI 运行在 ubuntu，而基线若在 macOS 生成，
   字体渲染差异会让 golden 断言必然失败（规范本身也写明 Golden 只在
   "稳定平台"才必须）。需要先决定基线在哪一类平台上生成与比对 ——
   例如统一在 CI 的 ubuntu 上生成基线，或把 Golden 拆成独立的工作流。
